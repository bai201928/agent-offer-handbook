# 第 6 章：JVM 第一条主线：对象放在哪里，又怎样被加载

## 本章目标

建立运行时内存区域、对象创建、类加载、引用和堆外内存的完整图。后续 GC 与故障排查都依赖这张图。

## 前置知识

完成 Java 运行和并发章节，理解线程、对象和类。

## 本章学习路径

```text
线程私有区域 → 共享堆/元空间 → 对象创建 → 类加载 → 引用强度 → 直接内存 → OOM 分类
```

> 本章不是按旧八股文件的出现顺序排列，而是按“先能运行，再解释原理，最后处理故障”的认知顺序组织。

### Q041：JVM 运行时内存区域分别存什么？

**题型**：JVM 核心题　｜　**频率**：★★★★★

**为什么现在学**：这是所有 GC、OOM、线程栈和类加载问题的地图。

#### 1. 先用人话理解

程序计数器和虚拟机栈是线程私有；堆和元空间主要共享。栈帧保存局部变量、操作数、动态链接和返回信息；堆保存对象实例；元空间保存类元数据；直接内存在 JVM 运行时数据区之外但常由 NIO 使用。

#### 2. 它在 JVM / 框架里怎么运行

1. 每个线程创建程序计数器和 Java 栈
2. 方法调用压入栈帧，返回后弹出
3. 对象通常在堆分配并由 GC 管理
4. 类加载后元数据进入本地内存中的元空间
5. JNI/native 调用使用本地方法相关能力
6. NIO DirectByteBuffer 可申请堆外直接内存

#### 3. 贯穿项目怎么用

Agent 会话、检索结果和 DTO 在堆；每个请求线程有自己的栈；大量动态代理类影响元空间；Netty 缓冲影响直接内存。

#### 4. 可读但容易出事故的写法

```java
// 只看 -Xmx，以为 JVM 总内存只有堆
java -Xmx2g -jar app.jar
```

#### 5. 更稳妥的企业级写法

```java
// 容量评估同时考虑堆、线程栈、元空间、直接内存和 native
java -Xms2g -Xmx2g -XX:MaxDirectMemorySize=512m -jar app.jar
```

#### 6. 2～3 分钟面试口述

> JVM 运行时数据区域可以先按线程私有和共享理解。程序计数器记录线程下一条字节码位置；虚拟机栈由栈帧组成，保存方法局部变量、操作数等；堆保存绝大多数对象实例，是 GC 主战场；方法区在 HotSpot 中主要由元空间实现，保存类元数据；本地方法栈服务 native 调用。直接内存不属于规范中的运行时数据区，但 NIO 和 Netty 大量使用。线上内存评估不能只看 Xmx，还要加线程栈、元空间、直接内存和 JVM native 开销。

#### 7. 面试官递进追问

- 运行时常量池属于哪里？
- 程序计数器为什么几乎不会 OOM？

**记忆钩子**：线程有计数器和栈，大家共享堆和类信息，NIO 还用堆外。

### Q042：堆和栈有什么区别？对象和引用到底放在哪里？

**题型**：高频基础题　｜　**频率**：★★★★★

**为什么现在学**：“对象都在堆、引用都在栈”只是入门近似，面试要说明边界。

#### 1. 先用人话理解

方法局部变量位于栈帧局部变量表，局部引用值指向对象；对象通常在堆。但 JIT 的逃逸分析可能标量替换，使对象不一定真实分配成完整堆对象。实例字段中的引用则随所属对象一起在堆中。

#### 2. 它在 JVM / 框架里怎么运行

1. 线程调用方法创建栈帧
2. 局部基本值和引用值进入局部变量表
3. `new` 请求对象内存并完成初始化
4. 引用值连接栈变量与堆对象
5. JIT 可对不逃逸对象进行消除或标量替换

#### 3. 贯穿项目怎么用

一次 Agent 请求方法返回后栈帧立即消失，但返回对象若仍被上层引用会继续存在；不要误以为方法结束对象一定回收。

#### 4. 可读但容易出事故的写法

```java
AgentResult build() {
  AgentResult r = new AgentResult();
  return r; // 方法结束但对象仍被调用方引用
}
```

#### 5. 更稳妥的企业级写法

```java
// 通过生命周期和可达性判断，不依赖“局部变量出栈=对象回收”
AgentResult result = service.build();
```

#### 6. 2～3 分钟面试口述

> 栈是线程私有的方法执行空间，方法调用产生栈帧，局部变量表可保存基本值和对象引用值；堆主要保存对象实例并由线程共享。局部引用出栈只代表这条引用消失，如果对象还被返回值、字段或集合引用，就不会回收。反过来，JIT 通过逃逸分析可能消除某些对象分配，所以“所有对象必然在堆”也不是严格结论。排障时应依据引用链和实际 JVM 数据，而不是只靠语法位置猜生命周期。

#### 7. 面试官递进追问

- 栈上能否保存对象本身？
- 逃逸分析有哪些常见优化？

**记忆钩子**：栈管方法执行，堆管对象生命周期；引用消失不等于对象立刻消失。

### Q043：一个对象从 `new` 到可用经历了什么？对象头里有什么？

**题型**：资深工程师题　｜　**频率**：★★★★☆

**为什么现在学**：它把类加载、内存分配、并发安全和锁机制连接起来。

#### 1. 先用人话理解

执行 new 前先确保类已初始化；JVM 在堆上分配空间、清零、设置对象头，再执行构造器。对象头通常包含运行时标记信息和类型指针，数组还包含长度；具体布局受 JVM、压缩指针和对象头优化影响。

#### 2. 它在 JVM / 框架里怎么运行

1. 检查目标类是否已经加载并初始化
2. 在 TLAB 或共享区域尝试分配内存
3. 将实例字段设为零值
4. 写入对象头、类型信息和必要对齐
5. 执行父类与当前类构造逻辑
6. 引用返回给调用代码并按 JMM 规则发布

#### 3. 贯穿项目怎么用

创建模型客户端或配置对象后，应通过构造器一次性建立有效状态；不能在对象尚未初始化完成时把 `this` 暴露给其他线程。

#### 4. 可读但容易出事故的写法

```java
class Client {
 Client() { Registry.register(this); init(); } // this 逸出，其他线程可能看到半初始化对象
}
```

#### 5. 更稳妥的企业级写法

```java
final class Client {
 private final Config config;
 Client(Config config) { this.config = requireNonNull(config); }
 static Client create(Config c) { return new Client(c); }
}
```

#### 6. 2～3 分钟面试口述

> 对象创建不是只有分配内存。JVM 先确保类已加载初始化，然后在堆或 TLAB 分配空间，设置零值和对象头，再执行构造器。对象头保存哈希、锁状态、GC 年龄等运行时标记以及类型指针，数组还需要长度；具体位数取决于 JVM 配置。工程上要避免构造期间 this 逸出，否则其他线程可能看到未完成初始化的对象。使用 final 字段和构造器完整校验有利于安全发布。

#### 7. 面试官递进追问

- TLAB 为什么能降低对象分配竞争？
- 对象一定有 identity hashCode 吗？

**记忆钩子**：先类可用，再分配清零，写对象头，最后构造；半成品不能外泄。

### Q044：类加载过程与类初始化触发条件是什么？

**题型**：JVM 核心题　｜　**频率**：★★★★★

**为什么现在学**：Spring 扫描、动态代理、SPI、热部署和 NoClassDefFoundError 都建立在类加载之上。

#### 1. 先用人话理解

类生命周期主线是加载、验证、准备、解析、初始化。准备阶段给静态变量分配空间并设零值；初始化阶段执行静态字段赋值和静态块。首次主动使用通常触发初始化，但访问编译期常量等场景可能不会。

#### 2. 它在 JVM / 框架里怎么运行

1. 加载：读取字节并创建 Class 元数据
2. 验证：检查格式、语义和字节码安全
3. 准备：分配类变量并设默认值
4. 解析：符号引用转直接引用，可按实现延迟
5. 初始化：执行 `<clinit>`，父类通常先于子类
6. 卸载通常要求对应类加载器也不可达

#### 3. 贯穿项目怎么用

自定义 Starter 或插件加载失败，要区分 ClassNotFound、NoClassDefFound、初始化异常和版本冲突。

#### 4. 可读但容易出事故的写法

```java
class Config {
 static AgentClient CLIENT = connectRemote(); // 类初始化做远程 I/O，启动难排障
}
```

#### 5. 更稳妥的企业级写法

```java
@Configuration
class Config {
 @Bean AgentClient client(Properties p) { return new AgentClient(p); }
}
```

#### 6. 2～3 分钟面试口述

> 类加载包括加载、验证、准备、解析和初始化。准备阶段只给静态变量分配并设置默认值，真正的显式赋值和静态块在初始化阶段执行。首次创建实例、调用静态方法、访问非编译期常量静态字段等主动使用会触发初始化，父类通常先初始化。项目中不应在静态初始化中做远程调用或复杂副作用，否则类初始化失败会演变成难定位的 NoClassDefFoundError。

#### 7. 面试官递进追问

- ClassNotFoundException 与 NoClassDefFoundError 有什么区别？
- 接口初始化与类初始化有何不同？

**记忆钩子**：加载拿字节，链接变可用，初始化才跑静态代码。

### Q045：类加载器和双亲委派解决什么？什么时候会打破？

**题型**：高频 JVM 题　｜　**频率**：★★★★★

**为什么现在学**：大厂常从双亲委派追问到 SPI、容器隔离和类冲突。

#### 1. 先用人话理解

类加载器负责按名字找到字节并定义 Class。双亲委派先让父加载器尝试，避免核心类重复和被恶意替换，也提高共享。但应用服务器、插件、SPI 和模块隔离可能需要子优先或线程上下文类加载器。

#### 2. 它在 JVM / 框架里怎么运行

1. Bootstrap 加载核心基础类
2. Platform 加载平台模块
3. Application 加载应用 classpath/module path
4. 自定义加载器可实现插件隔离
5. 同名类由不同加载器定义后，在 JVM 看来是不同类型
6. SPI 常通过 Thread Context ClassLoader 让上层代码发现下层实现

#### 3. 贯穿项目怎么用

多租户插件不能直接放进主应用 classpath；可用独立 ClassLoader 隔离版本，并在卸载时清理线程、缓存和 ThreadLocal 防止类加载器泄漏。

#### 4. 可读但容易出事故的写法

```java
URLClassLoader loader = new URLClassLoader(urls);
loadPlugin(loader); // 永久缓存 loader，插件类无法卸载
```

#### 5. 更稳妥的企业级写法

```java
try (URLClassLoader loader = new URLClassLoader(urls, apiLoader)) {
  Plugin p = loadPlugin(loader);
  p.close();
} // 同时清理线程和静态缓存
```

#### 6. 2～3 分钟面试口述

> 双亲委派是类加载请求优先交给父加载器，父找不到再由当前加载器处理。它避免核心类重复加载和随意替换，也便于共享。插件、应用服务器和 SPI 可能因为隔离或反向发现需求采用不同策略，例如线程上下文类加载器。同一个类名如果由不同类加载器定义，类型身份也不同。项目做插件热加载时，要同时管理类加载器、线程、ThreadLocal 和静态缓存，否则会发生 Metaspace 泄漏。

#### 7. 面试官递进追问

- 为什么 JDBC SPI 需要上下文类加载器？
- 类加载器泄漏怎样在堆转储中识别？

**记忆钩子**：父先找保核心，插件隔离会改规则；类身份等于类名加加载器。

### Q046：强、软、弱、虚引用分别适合什么场景？

**题型**：中高频题　｜　**频率**：★★★☆☆

**为什么现在学**：弱引用经常被机械地等同缓存，实际缓存语义和回收时机需要谨慎。

#### 1. 先用人话理解

强引用存在时对象不会因普通 GC 回收；软引用在内存压力下可能回收，但不适合作为可预测缓存；弱引用只要没有强引用，下一次相关 GC 即可回收；虚引用不能取对象，配合 ReferenceQueue 观察回收和管理堆外资源。

#### 2. 它在 JVM / 框架里怎么运行

1. 引用处理由 GC 在可达性分析后识别
2. SoftReference 回收策略依赖 JVM 与内存压力
3. WeakReference 常用于不应阻止对象生命周期的映射
4. PhantomReference 的 get 永远为 null
5. ReferenceQueue 用于接收已处理引用通知

#### 3. 贯穿项目怎么用

业务缓存应使用 Caffeine/Redis 的明确容量和 TTL；WeakHashMap 可用于元数据关联，但 Key 生命周期和并发边界必须清晰。

#### 4. 可读但容易出事故的写法

```java
Map<String, SoftReference<ModelClient>> cache = new HashMap<>();
// 回收不可预测，连接生命周期混乱
```

#### 5. 更稳妥的企业级写法

```java
Cache<String, ModelClient> cache = Caffeine.newBuilder()
 .maximumSize(1000).expireAfterAccess(Duration.ofMinutes(10)).build();
```

#### 6. 2～3 分钟面试口述

> 强引用是普通引用，只要存在强可达链对象就不会回收。软引用在内存压力下可能回收，但策略不可预测，现代业务缓存不应依赖它；弱引用不阻止对象回收，适合附加元数据等特定场景；虚引用不能获取对象，主要配合 ReferenceQueue 感知回收并清理堆外资源。项目缓存更应使用明确最大容量、TTL 和统计的 Caffeine 或 Redis。

#### 7. 面试官递进追问

- WeakHashMap 为什么不是通用线程安全缓存？
- Cleaner 与虚引用有什么关系？

**记忆钩子**：强引用保活，弱引用不拦 GC，虚引用只收通知；缓存要有明确策略。

### Q047：直接内存和 NIO 为什么快？它会怎样 OOM？

**题型**：项目深挖题　｜　**频率**：★★★★☆

**为什么现在学**：Netty、文件上传、向量数据和网络 I/O 会使用堆外内存，只盯堆监控会漏掉问题。

#### 1. 先用人话理解

DirectByteBuffer 在堆外分配 native 内存，I/O 时可减少 Java 堆数组到 native 缓冲区的额外复制，但分配释放成本较高。Java 对象仍在堆中保存地址与清理信息；若引用泄漏或释放不及时，会出现 Direct buffer memory OOM。

#### 2. 它在 JVM / 框架里怎么运行

1. 调用 allocateDirect 或框架池化分配堆外区域
2. 堆内 DirectByteBuffer 对象指向 native 地址
3. 操作系统 I/O 可直接使用该区域
4. 对象不可达后 Cleaner/引用处理触发释放，时间受 GC 影响
5. 池化框架自行复用并要求正确 release

#### 3. 贯穿项目怎么用

Netty 网关需监控 direct memory、PooledByteBufAllocator 指标和 leak detector；文件处理禁止把所有内容复制进堆。

#### 4. 可读但容易出事故的写法

```java
ByteBuffer buf = ByteBuffer.allocateDirect(100 * 1024 * 1024);
leaked.add(buf); // 长期强引用，直接内存持续增长
```

#### 5. 更稳妥的企业级写法

```java
ByteBuf buf = allocator.buffer();
try { use(buf); }
finally { buf.release(); }
```

#### 6. 2～3 分钟面试口述

> 直接内存位于 Java 堆外，NIO 可以让操作系统 I/O 直接使用该缓冲区，减少中间复制，但分配释放比普通堆数组更贵，所以框架常池化。DirectByteBuffer 对象本身仍在堆中，保存 native 地址；如果引用或池化资源泄漏，可能在堆看起来正常时抛 Direct buffer memory OOM。排障需要同时看堆外指标、进程 RSS、Netty allocator 和对象引用，不能只调大 Xmx。

#### 7. 面试官递进追问

- mmap 与 direct buffer 有什么区别？
- 为什么 GC 不频繁时直接内存可能释放不及时？

**记忆钩子**：堆外省复制但不归堆容量管；使用后要归还，监控看 RSS 和 direct。

### Q048：内存泄漏、OOM 和 StackOverflowError 有什么区别？

**题型**：核心故障题　｜　**频率**：★★★★★

**为什么现在学**：错误分类决定你该看堆转储、线程数量、递归栈还是直接内存。

#### 1. 先用人话理解

内存泄漏是不用的对象仍被引用，GC 无法回收；OOM 是某区域无法满足分配请求，可能由泄漏、容量不足、瞬时峰值或资源数量过多导致；StackOverflowError 通常是单线程调用栈过深。

#### 2. 它在 JVM / 框架里怎么运行

1. 堆 OOM 看对象占用和引用链
2. Metaspace OOM 看类数量和类加载器
3. Direct buffer OOM 看堆外缓冲与释放
4. unable to create native thread 看线程数、栈和系统限制
5. StackOverflowError 看递归或巨大栈帧
6. GC overhead 等问题看回收收益和分配速率

#### 3. 贯穿项目怎么用

Agent 长会话缓存未淘汰导致堆泄漏；每请求新建平台线程导致 native thread OOM；递归 Agent 图无终止条件导致 StackOverflow。

#### 4. 可读但容易出事故的写法

```java
void run(Node n) { run(n.next()); } // 无终止条件
```

#### 5. 更稳妥的企业级写法

```java
void run(Node start) {
  for (Node n=start; n!=null; n=n.next()) process(n);
}
```

#### 6. 2～3 分钟面试口述

> 内存泄漏描述的是对象已无业务价值但仍被引用，GC 无法回收；OOM 是某个内存或资源区域无法继续分配，泄漏只是原因之一；StackOverflowError 通常来自递归过深或栈帧过大。排障要先看错误类型：Java heap space 分析堆转储，Metaspace 看类加载器，Direct buffer memory 看堆外，unable to create native thread 看线程与系统限制，StackOverflow 看调用链。不能看到内存错误就只调大 Xmx。

#### 7. 面试官递进追问

- 内存泄漏一定会 OOM 吗？
- 对象增长是业务增长还是泄漏怎样区分？

**记忆钩子**：泄漏是留住不该留的，OOM 是分配失败，栈溢出是调用太深。

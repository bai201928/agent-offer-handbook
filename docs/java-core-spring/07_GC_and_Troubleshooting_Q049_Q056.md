# 第 7 章：JVM 第二条主线：对象什么时候回收，线上怎样定位

## 本章目标

从可达性、分代和收集器进入 G1、ZGC、STW、OOM 与 CPU/GC 联合排障。CMS 仅作为历史对照，不再当现代项目首选。

## 前置知识

完成第 6 章，知道对象、堆、类加载器和直接内存。

## 本章学习路径

```text
可达性 → 回收算法 → 分代 → G1 → ZGC → STW/安全点 → OOM → CPU与延迟排障
```

> 本章不是按旧八股文件的出现顺序排列，而是按“先能运行，再解释原理，最后处理故障”的认知顺序组织。

### Q049：JVM 怎样判断对象是不是垃圾？GC Roots 有哪些？

**题型**：JVM 核心题　｜　**频率**：★★★★★

**为什么现在学**：回收器必须先判断对象是否仍可能被程序使用，引用计数并不是 HotSpot 主流判断方式。

#### 1. 先用人话理解

JVM 主要通过可达性分析：从一组 GC Roots 出发沿引用图遍历，无法到达的对象才进入可回收候选。Roots 包括线程栈中的引用、类静态字段、JNI 引用、活动同步器等。

#### 2. 它在 JVM / 框架里怎么运行

1. 在安全点或并发标记协议下获得根引用集合
2. 从 Roots 沿对象字段遍历引用图
3. 标记强可达及不同引用强度对象
4. 处理 Reference、finalization/清理等特殊机制
5. 未标记对象由对应收集算法回收或整理

#### 3. 贯穿项目怎么用

静态 Map、线程池 ThreadLocal、监听器和类加载器都可能成为长生命周期引用链，导致 Agent 会话对象无法回收。

#### 4. 可读但容易出事故的写法

```java
static final Map<String, AgentRun> RUNS = new HashMap<>();
// 完成后从不删除，所有 run 始终可达
```

#### 5. 更稳妥的企业级写法

```java
Cache<String, AgentRun> runs = Caffeine.newBuilder()
 .maximumSize(10_000).expireAfterWrite(Duration.ofHours(1)).build();
```

#### 6. 2～3 分钟面试口述

> HotSpot 判断垃圾主要使用可达性分析，而不是简单引用计数。GC 从线程栈引用、类静态字段、JNI 句柄等 GC Roots 出发遍历对象图，无法从 Roots 到达的对象才有机会回收。内存泄漏往往不是对象不能被 GC，而是它仍被静态集合、ThreadLocal、监听器或类加载器错误持有。分析堆转储时要看 dominator tree 和到 GC Root 的引用路径，找出谁在持有对象。

#### 7. 面试官递进追问

- 为什么引用计数难以处理循环引用？
- 对象不可达后一定立即回收吗？

**记忆钩子**：从 Roots 能走到就活着，走不到才是回收候选。

### Q050：标记清除、复制、标记整理分别解决什么？

**题型**：高频 JVM 题　｜　**频率**：★★★★★

**为什么现在学**：现代收集器是这些基本算法的组合，先懂算法才能理解分代和 Region。

#### 1. 先用人话理解

标记清除直接回收死亡对象但产生碎片；复制把存活对象搬到新区域，分配快但需要备用空间；标记整理把存活对象向一端移动，减少碎片但搬移成本较高。

#### 2. 它在 JVM / 框架里怎么运行

1. 标记阶段识别存活对象
2. 清除算法回收空洞并维护空闲列表
3. 复制算法把存活对象复制到目标区并整体重置源区
4. 整理算法计算新地址、更新引用并移动对象
5. 现代 GC 会按区域、代和并发阶段组合这些方法

#### 3. 贯穿项目怎么用

大批短命 Prompt 中间对象适合年轻代复制回收；长寿命缓存与大对象需要避免长期碎片和错误晋升。

#### 4. 可读但容易出事故的写法

```java
// 大量临时字符串和 JSON 树长期放入全局集合
history.add(parseEveryResponse(raw));
```

#### 5. 更稳妥的企业级写法

```java
// 及时转成紧凑领域对象，临时解析树不跨请求保存
AgentEvent event = toEvent(parse(raw));
```

#### 6. 2～3 分钟面试口述

> 三种基本回收思路各有取舍。标记清除不移动对象，但会产生内存碎片；复制算法把存活对象复制到另一块区域，适合存活率低的年轻代，分配也很快；标记整理把存活对象压到一端，减少碎片但需要移动和更新引用。现代 G1、ZGC 等并不是只用一种算法，而是结合 Region、分代和并发处理。回答时应从存活率、暂停、吞吐和空间开销解释选择。

#### 7. 面试官递进追问

- 对象移动后引用怎样更新？
- 为什么复制算法适合短命对象？

**记忆钩子**：清除快但碎，复制适合少量存活，整理省碎片但要搬对象。

### Q051：分代假设、Young GC 和 Full GC 怎么理解？

**题型**：核心面试题　｜　**频率**：★★★★★

**为什么现在学**：旧资料常把 Minor、Major、Full 混为固定标准术语，现代回答要说明收集器差异和具体日志。

#### 1. 先用人话理解

分代基于多数对象朝生夕死、少数长期存活。年轻代频繁回收短命对象，存活对象逐步晋升；老年代回收频率较低。Full GC 通常意味着覆盖更广区域和更长暂停，但触发与含义依收集器、JDK 日志而定。

#### 2. 它在 JVM / 框架里怎么运行

1. 对象通常先在年轻代/Eden 或对应 Region 分配
2. 年轻代空间压力触发 Young GC
3. 存活对象复制到 Survivor 或晋升老年代
4. 老年代占用、晋升失败、显式 GC 或收集器策略可能触发更广回收
5. 使用统一 GC 日志确认原因，而不是只靠名词猜

#### 3. 贯穿项目怎么用

Agent 平台出现 p99 抖动时查看分配速率、Young GC 周期、晋升量和老年代占用；不能看到 GC 次数多就认定问题。

#### 4. 可读但容易出事故的写法

```java
System.gc(); // 业务代码主动请求 Full GC，制造暂停
```

#### 5. 更稳妥的企业级写法

```java
// 通过 -Xlog:gc* 与 JFR 观察根因，业务代码不主动 GC
```

#### 6. 2～3 分钟面试口述

> 分代假设认为多数对象生命周期短，因此年轻代用更频繁、适合低存活率的回收，长期存活对象进入老年代。Young GC 不一定是坏事，关键看暂停、频率和晋升；Full GC 通常覆盖范围更广、暂停更明显，但不同收集器的术语和触发机制不同，应以实际 GC 日志为准。项目排障要同时看对象分配率、晋升、老年代增长、暂停分位数和吞吐，不能只统计 GC 次数。

#### 7. 面试官递进追问

- 大对象为什么可能跳过普通年轻代路径？
- `System.gc()` 是否一定执行 Full GC？

**记忆钩子**：年轻代收短命，老年代放长寿命；看日志原因，不死背名词。

### Q052：G1 的 Region、Remembered Set 和混合回收是什么？

**题型**：JVM 高频高薪题　｜　**频率**：★★★★★

**为什么现在学**：现代 HotSpot 默认在多数平台使用 G1，面试仍只讲 CMS 会显得过时。

#### 1. 先用人话理解

G1 把堆划分为等大小 Region，Region 动态承担 Eden、Survivor、Old 或 Humongous 角色。它按收益选择回收集合，借助 Remembered Set 跟踪跨 Region 引用，并通过并发标记识别老年代垃圾，随后执行 Mixed GC。

#### 2. 它在 JVM / 框架里怎么运行

1. Young GC 回收年轻 Region
2. 并发标记周期估算老年代 Region 存活率
3. 写屏障维护跨 Region 引用信息
4. Mixed GC 同时回收年轻 Region 和收益较高的老 Region
5. Humongous 对象占用连续 Region，需要特别监控
6. MaxGCPauseMillis 是目标而非硬保证

#### 3. 贯穿项目怎么用

长文本、Embedding 大数组和批量 JSON 可能形成 Humongous 对象；应优化批次和对象表示，而不是只调暂停目标。

#### 4. 可读但容易出事故的写法

```java
byte[] giant = loadEntireKnowledgeBase(); // 巨型对象与内存尖峰
```

#### 5. 更稳妥的企业级写法

```java
try (InputStream in = source.openStream()) {
  processInChunks(in, 4 * 1024 * 1024);
}
```

#### 6. 2～3 分钟面试口述

> G1 将堆划分为多个等大小 Region，而不是固定连续的新生代和老年代区域。Region 可动态承担不同角色。G1 通过 Remembered Set 跟踪跨 Region 引用，年轻代回收时不必扫描整个堆；并发标记后，它会选择垃圾比例高的老 Region 与年轻 Region 一起做 Mixed GC，目标是在可预测暂停和吞吐之间平衡。超过 Region 一半的大对象会按 Humongous 处理，批量文本和大数组应重点监控。

#### 7. 面试官递进追问

- G1 为什么仍会发生 Full GC？
- RSet 会带来什么内存与写屏障成本？

**记忆钩子**：G1 把堆切 Region，按收益挑区域；RSet 记跨区引用，Mixed 回收年轻和部分老区。

### Q053：G1 和 ZGC 怎么选？CMS 还需要背到什么程度？

**题型**：资深工程师题　｜　**频率**：★★★★☆

**为什么现在学**：收集器选型要基于暂停、吞吐、堆规模和可观测性，而不是一句“ZGC 最先进”。

#### 1. 先用人话理解

G1 是多数场景默认的平衡型收集器；ZGC 以并发搬移和极低暂停为目标，适合大堆、低延迟，但会付出额外 CPU、内存和吞吐成本。CMS 已从现代 JDK 移除，面试只需说明历史并发标记清除与碎片问题。

#### 2. 它在 JVM / 框架里怎么运行

1. 先明确 SLA：吞吐优先还是极低暂停
2. 使用默认 G1 建立基线
3. 若大堆下暂停仍无法满足，再评估 ZGC
4. 比较相同业务负载下 CPU、RSS、吞吐和 p99/p999
5. 验证容器内存上限与回收器自适应行为

#### 3. 贯穿项目怎么用

在线 Agent API 对尾延迟敏感可评估 ZGC；离线索引构建更关注吞吐，G1 或其他策略可能更合适。

#### 4. 可读但容易出事故的写法

```java
// 因为“ZGC 新”就直接切换
java -XX:+UseZGC -jar app.jar
```

#### 5. 更稳妥的企业级写法

```java
// 同负载 A/B：记录吞吐、p99、CPU、RSS、分配率、GC 暂停后再决策
```

#### 6. 2～3 分钟面试口述

> 在现代 JDK 中，G1 是多数平台默认收集器，适合通用服务，在吞吐和可预测暂停间折中。ZGC 把更多标记和搬移工作并发化，目标是亚毫秒级停顿，更适合大堆、严格低延迟场景，但可能增加 CPU、内存和吞吐成本。选型要通过相同负载压测，而不是只看新旧。CMS 已在现代 JDK 移除，了解其并发标记清除、浮动垃圾和碎片问题即可，不应作为当前项目方案。

#### 7. 面试官递进追问

- ZGC 为什么也不能保证业务 p99 一定低？
- 容器 CPU 限额如何影响并发 GC？

**记忆钩子**：G1 做默认平衡，ZGC 买低停顿；CMS 只讲历史问题。

### Q054：Stop-The-World、安全点和 safepoint bias 是什么？

**题型**：高薪 JVM 题　｜　**频率**：★★★★☆

**为什么现在学**：业务延迟尖刺不只来自长 GC，也可能来自线程到达安全点、类重定义和其他 VM 操作。

#### 1. 先用人话理解

STW 表示 JVM 暂停应用线程执行某些需要一致视图的操作。线程通常在可安全检查对象和栈状态的位置停下。暂停时间包含到达安全点的时间和 VM 操作时间，不能把所有 pause 都简单等同回收算法。

#### 2. 它在 JVM / 框架里怎么运行

1. JVM 发起全局或局部协调请求
2. 线程在轮询点/安全点协议处停下
3. VM 执行根扫描、对象重定位、去优化等操作
4. 恢复应用线程
5. 日志和 JFR 分离 safepoint time 与具体 GC phase

#### 3. 贯穿项目怎么用

Agent 服务低频出现 2 秒停顿，要结合 GC log、safepoint log、JFR 和操作系统调度判断，不直接调堆。

#### 4. 可读但容易出事故的写法

```java
// 只看平均 GC pause，忽略 p99 和 safepoint
report(avgPause);
```

#### 5. 更稳妥的企业级写法

```java
// 统一采集 JFR、-Xlog:gc*,safepoint 和请求 trace 时间线
```

#### 6. 2～3 分钟面试口述

> Stop-The-World 是应用线程被暂停以获得一致运行时视图，并不只发生在某一种 GC。线程需要到达 JVM 能安全检查栈和对象引用的位置，暂停总时长包括线程到达安全点以及执行 VM 操作的时间。长时间不进入可轮询位置、去优化、类操作等也可能影响停顿。线上应把请求 Trace、GC 日志、safepoint 日志和 JFR 时间线对齐，不能只看平均 GC 暂停。

#### 7. 面试官递进追问

- 什么是 time to safepoint？
- JNI 临界区会怎样影响 GC 协调？

**记忆钩子**：暂停时间=等线程停下+VM 真正干活；别把所有停顿都叫 GC。

### Q055：遇到 Java heap space、Metaspace、Direct buffer memory 怎么排查？

**题型**：项目故障题　｜　**频率**：★★★★★

**为什么现在学**：大厂项目深挖关注可复现的排障流程，而不是一句“加内存”。

#### 1. 先用人话理解

先保存现场，再分类区域，再分析增长来源。堆问题用 HeapDump、JFR、类直方图和引用链；元空间看类数量与加载器；直接内存看 RSS、NMT、框架池化指标。调大上限只能缓解容量不足，不能修复泄漏。

#### 2. 它在 JVM / 框架里怎么运行

1. 记录异常、容器限制、JVM 参数和负载时间线
2. 开启 HeapDumpOnOutOfMemoryError 或保留安全转储方案
3. 用 `jcmd GC.class_histogram`、MAT/JProfiler 看大对象与 dominator
4. Metaspace 检查重复类加载器和动态代理/脚本类
5. Direct memory 检查 native memory、Netty leak 与 buffer 引用
6. 修复后用相同流量和长稳压测验证

#### 3. 贯穿项目怎么用

会话缓存 OOM 要区分租户增长、TTL 缺失、单条会话过大或请求对象被 ThreadLocal 持有。

#### 4. 可读但容易出事故的写法

```java
// 第一反应只改参数
-Xmx16g
```

#### 5. 更稳妥的企业级写法

```java
// 保留现场 + 限制缓存 + 修复引用链 + 长稳验证
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps
```

#### 6. 2～3 分钟面试口述

> OOM 排查先分区域和保存现场。Java heap space 用堆转储、类直方图、Dominator Tree 和到 GC Root 路径定位大对象及持有者；Metaspace 重点看类数量、类加载器是否重复且无法卸载；Direct buffer memory 同时看进程 RSS、NMT、Netty 池和泄漏检测。还要结合流量、对象大小和容器限制判断是泄漏、容量不足还是瞬时峰值。调大内存可以止血，但必须用相同负载长稳测试验证根因已消失。

#### 7. 面试官递进追问

- 线上 HeapDump 很大时怎样降低风险？
- 为什么类加载器泄漏会同时在堆和元空间体现？

**记忆钩子**：先保现场，再分区域，再找持有链；加内存只能止血。

### Q056：CPU 飙高、频繁 GC、线程堆积和接口慢怎样联合排查？

**题型**：资深项目深挖题　｜　**频率**：★★★★★

**为什么现在学**：真实故障往往不是单一 JVM 指标，必须把线程、GC、外部依赖和业务 Trace 组合起来。

#### 1. 先用人话理解

先判断 CPU 是业务计算、锁自旋、GC、序列化还是内核开销；再用线程转储/JFR 找热点栈，与请求 Trace 和依赖指标对齐。GC 高要区分分配率高、存活率高、堆太小或泄漏。

#### 2. 它在 JVM / 框架里怎么运行

1. 确认主机/容器 CPU、限流和进程线程级使用
2. 连续采集 JFR 或 async-profiler，避免只看一次 jstack
3. 检查 GC CPU、暂停、分配率和老年代趋势
4. 检查线程池活跃数、队列、锁等待与虚拟线程状态
5. 检查数据库、Redis、模型 API 和网络延迟
6. 形成时间线并复现，修复后压测回归

#### 3. 贯穿项目怎么用

Agent 响应慢可能是 JSON 构造分配过多触发 GC，也可能是模型连接池耗尽导致线程等待；两者治理完全不同。

#### 4. 可读但容易出事故的写法

```java
// 只看到 CPU 高就扩容实例，根因继续存在
```

#### 5. 更稳妥的企业级写法

```java
// JFR + trace + GC log + pool metrics 建立同一时间线
```

#### 6. 2～3 分钟面试口述

> 综合排障我会先分类 CPU 来源，再建立时间线。查看容器 CPU 与线程级消耗，连续采集 JFR 或 profiler 找热点方法、锁等待和分配热点；同时看 GC 暂停、GC CPU、分配率、老年代趋势，线程池队列和外部依赖延迟。CPU 高可能是业务循环、CAS 自旋、序列化、GC 或内核调用；接口慢也可能只是下游阻塞。只有把 JVM、线程池、Trace、数据库和模型 API 指标对齐，才能避免错误扩容。

#### 7. 面试官递进追问

- 一次 jstack 为什么可能误导？
- 高 CPU 与高 load average 有什么区别？

**记忆钩子**：先分类资源，再对齐时间线；JVM、线程池、Trace、下游一起看。

## Q07. 为什么 InnoDB 索引使用 B+树，而不是二叉树或 Hash？

> **题型**：高频原理题　｜　**实际难度**：中等　｜　**面试频率**：★★★★★　｜　**重要性**：★★★★★

### ① 为什么现在学习这题
从页和磁盘访问出发理解 B+树，后面的联合索引与范围查询才不是口诀。

### ② 先建立一个具体画面
一本字典不是每个字都从第一页找；B+树用少量层级导航到目标页，并让范围记录在叶子层顺序相邻。

### ③ 从直觉进入标准概念
B+树适合数据库页访问：多路分支使树高低；数据集中在叶子层；叶子页有序相连，支持等值、范围、排序和游标扫描。普通二叉树层数高，Hash 不天然支持范围和排序。

### ④ 深入原理与源码主链

```text
row_search_mvcc
→ btr_cur_search_to_nth_level
→ 从根页逐层选择子页
→ 到达叶子页并定位记录
```

B+树节点是 InnoDB 页，重点是减少页访问，而不只是减少 CPU 比较次数。范围查询定位起点后，可沿相邻叶子页顺序读取。

### ⑤ 企业级边界与演进
索引键过宽会降低扇出；随机宽主键增加页分裂和二级索引体积；低选择性条件仍可能扫描大量叶子页；索引过多放大写入、Redo 和复制成本。

### ⑥ 最小案例

```sql
KEY idx_run_tenant_status_time
(tenant_id, status, created_at DESC, id DESC)
```

先定位租户和状态区间，再按叶子顺序读取 50 条。

### ⑦ 本题小结
> B+树以高扇出、低树高和有序叶子适配数据库页与范围查询。

### ⑧ 2～3 分钟面试口述
“B+树以页为节点，非叶子页能保存大量导航键，所以扇出高、树高低；叶子页按键有序并相连，既支持等值，也支持范围、排序和前缀扫描。二叉树层数高，Hash 不擅长范围。NexusAgent 的列表按 tenant、status 过滤并按时间排序，联合 B+树能快速定位连续区间并返回前 50 条。MySQL 优化的核心是减少实际页访问。”

### ⑨ 追问
- B+树范围查询为什么高效？
- 随机主键和顺序主键如何取舍？

> **记忆句**：B+树层级低、页友好、叶子有序。

## Q08. 什么是聚簇索引、二级索引和回表？

> **题型**：高频原理题　｜　**实际难度**：中等　｜　**面试频率**：★★★★★

### ① 为什么现在学习这题
理解二级索引叶子存主键，才能看懂回表、覆盖索引和主键宽度。

### ② 具体画面
按 status 的二级索引找到 status 与主键；要取 Prompt 时还要拿主键去聚簇索引找整行。

### ③ 标准概念
聚簇索引叶子保存整行，通常使用主键；二级索引叶子保存“二级键 + 主键”。通过二级索引找到主键后，再访问聚簇索引取其他列，叫回表。

### ④ 深入原理

```text
扫描二级叶子
→ 取得二级键与主键
→ 根据主键访问聚簇树
→ 结合 Undo 判断可见版本
→ 返回投影列
```

主键会复制到每个二级索引，宽 UUID 字符串会放大全表索引。

### ⑤ 企业级边界
减少回表可以使用高选择性条件、窄覆盖索引、显式投影和 Keyset Pagination，但不能为了覆盖把大正文塞进索引。

### ⑥ 最小案例
Run 列表只返回 `id、agent_id、status、created_at`，可由联合索引覆盖；详情页再按主键查询完整行。

### ⑦ 小结
> 聚簇叶子存整行，二级叶子存二级键和主键。

### ⑧ 2～3 分钟面试口述
“InnoDB 的聚簇索引通常是主键 B+树，叶子保存整行；二级索引叶子保存二级键和主键。通过二级索引找到主键后，再访问聚簇索引取其他列就是回表。回表可能产生随机页访问，主键太宽也会让所有二级索引变宽。列表可适度覆盖短字段，但不能把 Prompt、JSON 等大字段全部加入索引。”

### ⑨ 追问
- 宽主键怎样放大二级索引？
- 什么场景回表完全可接受？

> **记忆句**：二级叶子带主键，缺列再回聚簇树。

## Q09. 联合索引的字段顺序应该怎样设计？

> **题型**：高频设计题　｜　**实际难度**：中等偏上　｜　**面试频率**：★★★★★

### ① 为什么现在学习这题
从真实 SQL 推导列顺序，避免机械背“区分度最高放最前”。

### ② 具体画面
查询先按 tenant 和 status 缩小，再按 created_at、id 排序分页，索引应服务这条路径。

### ③ 标准概念
设计顺序应综合等值条件、范围、排序、分组、分页和投影。多租户表通常先保证 `tenant_id`；连续等值前缀缩小范围；范围和排序列按访问路径排列；唯一列作为稳定排序尾键；少量短字段可用于覆盖。

### ④ 深入原理
联合 B+树按复合键字典序排列。遇到范围后，后续列通常难以继续缩小同一搜索边界，但仍可能用于过滤、覆盖或排序，不能简单说“全部失效”。

### ⑤ 企业级边界
基于查询集合设计索引，评估冗余、写放大、真实租户分布、在线 DDL 和副本延迟。遗漏 tenant_id 可能是数据隔离错误，不只是性能问题。

### ⑥ 最小案例

```sql
WHERE tenant_id=? AND status=?
  AND (created_at,id)<(?,?)
ORDER BY created_at DESC,id DESC
LIMIT 50
```

候选索引：`(tenant_id,status,created_at DESC,id DESC)`。

### ⑦ 小结
> 联合索引从完整查询模式推导，而不是只看区分度。

### ⑧ 2～3 分钟面试口述
“联合索引顺序不能只看区分度。我会先分析等值、范围、排序、分页和返回列。对于 tenant_id、status 等值，created_at、id 游标和倒序列表，可使用 tenant_id、status、created_at、id。B+树按联合键字典序排列，连续等值前缀逐步缩小区间；遇到范围后，后续列可能仍参与过滤、覆盖或排序。最终必须用真实数据和 EXPLAIN ANALYZE 验证。”

### ⑨ 追问
- 范围条件后的列是否完全无用？
- 多个查询如何共享索引？

> **记忆句**：等值前缀定范围，范围排序接在后。

## Q10. 什么是覆盖索引？覆盖列是不是越多越好？

> **题型**：高频优化题　｜　**实际难度**：中等　｜　**面试频率**：★★★★★

### ① 为什么现在学习这题
覆盖索引是减少回表的手段，不是把整张表复制进索引。

### ② 具体画面
列表只返回几个短字段时可以覆盖；把 MEDIUMTEXT Prompt 放入索引会让写入、缓存和复制都变重。

### ③ 标准概念
查询需要的过滤、排序和返回列都能从二级索引获得，无需访问聚簇索引，叫覆盖索引。它减少回表，但会让索引变宽，增加空间、写放大、Redo、Binlog 和副本应用成本。

### ④ 深入原理
执行器根据索引元数据判断所需列能否直接返回。即使 Extra 显示 `Using index`，扫描百万条覆盖记录仍可能很慢。

### ⑤ 企业级边界
适合覆盖高频列表的短小稳定列；不适合 TEXT、JSON、大 VARCHAR、低频列和频繁更新列。可使用 Invisible Index 验证冗余索引退出。

### ⑥ 最小案例
Run 列表可覆盖 `id、agent_id、status、created_at`，不会把 Prompt 和 result_json 加入索引。

### ⑦ 小结
> 覆盖索引用空间和写成本换回表减少。

### ⑧ 2～3 分钟面试口述
“查询需要的列都能从某个二级索引取得，不再访问聚簇索引，就是覆盖索引。它减少回表和随机页访问，但覆盖列越多，索引越宽，写入、Redo、Binlog 和副本重放成本都会增加。Run 列表可覆盖固定短字段，Prompt、Trace 等大正文不应进入宽索引。”

### ⑨ 追问
- `Using index` 是否一定代表 SQL 快？
- Invisible Index 有什么作用？

> **记忆句**：覆盖减少回表，宽索引增加写放大。

## Q11. EXPLAIN 和 EXPLAIN ANALYZE 有什么区别？

> **题型**：高频工具题　｜　**实际难度**：中等　｜　**面试频率**：★★★★★

### ① 为什么现在学习这题
学会用真实执行数据验证计划，而不是只看 key、type 和 Extra。

### ② 具体画面
EXPLAIN 像导航预估路线，EXPLAIN ANALYZE 像真实开车后记录每段时间和车辆数。

### ③ 标准概念
`EXPLAIN` 展示优化器估算计划；`EXPLAIN ANALYZE` 会真实执行并显示各迭代器的实际时间、行数和 loops。

### ④ 深入原理

```text
Nested Loop
→ 外层 Read()
→ 内层重复 Read()
→ 统计 actual rows / loops / time
```

最大价值是发现“估算 10 行、实际 10 万行”的基数误判。节点时间包含子节点，不能简单相加。

### ⑤ 企业级边界
先由 Trace 和 digest 定位 SQL，再在受控环境使用 ANALYZE。写语句或极重查询会真实执行，生产使用要谨慎。

### ⑥ 最小案例
外层实际 20 万行，内层 loops=200000；即使内层单次很快，总成本也被循环放大。

### ⑦ 小结
> EXPLAIN 看估算，ANALYZE 看真实 rows、time 与 loops。

### ⑧ 2～3 分钟面试口述
“EXPLAIN 展示优化器的估算计划，不真正执行；EXPLAIN ANALYZE 会执行 SQL，给出实际时间、行数和循环次数。我重点比较 estimated rows 与 actual rows，并结合 loops 判断总工作量。若差距很大，通常检查统计信息、数据倾斜、列间相关性和索引模型。ANALYZE 会真实执行，生产对重查询和写语句要谨慎。”

### ⑨ 追问
- ANALYZE 为什么要谨慎在线执行？
- rows 与 loops 如何结合理解？

> **记忆句**：估算用 EXPLAIN，事实用 ANALYZE。

## Q12. 已经有索引，优化器为什么仍可能选择全表扫描？

> **题型**：资深优化题　｜　**实际难度**：中等偏上　｜　**面试频率**：★★★★☆

### ① 为什么现在学习这题
优化器按成本选路；这题连接统计信息、数据倾斜与查询设计。

### ② 具体画面
有高速路不代表一定走它；如果要经过 90% 的记录并频繁回表，全表顺序扫描可能更便宜。

### ③ 标准概念
条件命中比例高、回表多、表很小、索引不覆盖或统计估算索引收益低时，全表扫描可能更合理。误选还可能来自统计陈旧、数据倾斜、隐式转换、列函数和参数分布差异。

### ④ 深入原理
优化器估算访问行、页读取、回表、Join、排序和临时表成本。`ANALYZE TABLE` 更新统计，直方图补充值分布。`FORCE INDEX` 不会修复错误模型。

### ⑤ 企业级边界
先比较估算和实际，再检查条件、统计、直方图和联合索引；Hint 只能作为有验证和退出条件的临时稳定化措施。

### ⑥ 最小案例
小租户 RUNNING 占 1%，超级租户占 90%，相同索引成本完全不同。

### ⑦ 小结
> 有索引不等于索引路径成本最低。

### ⑧ 2～3 分钟面试口述
“优化器选择估算成本最低的计划。有索引但命中比例很高、需要大量回表或表很小时，全表扫描可能更便宜。误选也可能来自统计信息陈旧、数据倾斜、隐式类型转换和索引前导列不匹配。我会用 EXPLAIN ANALYZE 比较估算与实际，检查 SQL、统计和联合索引，FORCE INDEX 只作为有退出条件的临时手段。”

### ⑨ 追问
- 统计信息和直方图分别解决什么问题？
- 为什么测试库计划正常、生产异常？

> **记忆句**：索引只是候选路径，优化器按总成本选路。

## Q13. 线上 Run 列表出现慢 SQL，你会怎样定位并治理？

> **题型**：项目深挖题　｜　**实际难度**：中等偏上　｜　**面试频率**：★★★★★

### ① 为什么现在学习这题
把索引知识放进完整排障闭环：止血、定位、修复、回放与防回归。

### ② 具体画面
超级租户翻到第 2000 页后接口变慢，需要先判断连接等待、锁、扫描、排序还是结果传输。

### ③ 标准流程

```text
接口 Trace
→ 连接等待和 SQL 时间分段
→ digest / Slow Log / Performance Schema
→ EXPLAIN
→ 受控 EXPLAIN ANALYZE
→ 修 SQL、索引、统计或数据模型
→ 真实流量回放
→ 灰度与回归监控
```

### ④ 深入原理

```text
深分页 OFFSET
→ 扫描并丢弃大量记录
→ 回表和 filesort
→ 返回宽行
→ 连接持有时间增长
```

改用 Keyset：

```sql
WHERE tenant_id=?
  AND (created_at,id)<(?,?)
ORDER BY created_at DESC,id DESC
LIMIT 50;
```

### ⑤ 企业级边界
先限制最大页深、结果大小、执行时间和并发；保护连接池；不要在主库高峰直接执行极重 ANALYZE；修复后用大租户和混合读写回放。

### ⑥ 最小案例
`LIMIT 100000,50` 改成稳定游标 `(created_at,id)`，配合联合索引、窄投影和历史归档。

### ⑦ 小结
> 慢 SQL 治理从端到端证据开始，以真实回放和防回归结束。

### ⑧ 2～3 分钟面试口述
“我先区分接口是在等连接、等锁、执行慢还是传输慢，并对失控查询限时限并发。然后通过 Trace、digest、Slow Log 和 Performance Schema 找到 SQL 与真实参数，查看 rows_examined、rows_sent、锁时间和结果字节，再用 EXPLAIN 和受控 ANALYZE 验证估算与实际。Run 列表通常会把 SELECT * 改成窄投影，联合索引匹配 tenant、status、created_at、id，并把 OFFSET 深分页改成 Keyset。最后用真实租户比例和混合读写回放，监控 P99、写放大和副本延迟。”

### ⑨ 追问
- Keyset Pagination 如何避免重复或漏项？
- 索引上线后写 P99 上升怎么办？

> **记忆句**：先止血分段，再用真实参数修复和回归。

## Q23. Redo Log、Undo Log 和 Binlog 有什么区别？

> **题型**：高频日志题｜**实际难度**：中等｜**频率**：★★★★★

### ① 为什么现在学
先分清三种日志各自服务于回滚、恢复和复制，后面的两阶段提交才不会混乱。

### ② 具体画面
Undo 像撤销记录；Redo 像修改完成后的恢复凭证；Binlog 像按事务记录的业务变更流水。

### ③ 标准概念

```text
Undo Log
  → 保存修改前信息
  → 事务回滚
  → MVCC 历史版本

Redo Log
  → InnoDB 物理/页级恢复信息
  → WAL
  → 崩溃恢复已提交修改

Binlog
  → MySQL Server 层事务事件
  → 主从复制、CDC、增量与时间点恢复
```

### ④ 深入原理
修改记录时，InnoDB 先生成 Undo，再修改 Buffer Pool 页并写 Redo。数据页可以稍后刷盘。Server 层还要把事务写入 Binlog，因此提交需要协调两个日志系统。

### ⑤ 企业级边界
日志不是备份的替代品。误删、错误业务更新也会被正确记录和复制；仍需全量备份、Binlog 保留、恢复演练和业务对账。

### ⑥ 最小案例
事务将 Run 从 RUNNING 改为 SUCCEEDED：Undo 可恢复旧状态；Redo 可在宕机后重做新状态；Binlog 将这笔事务复制到副本并供 CDC 使用。

### ⑦ 小结
> Undo 回滚与 MVCC，Redo 崩溃恢复，Binlog 复制与增量恢复。

### ⑧ 2～3 分钟口述
“Undo、Redo 和 Binlog 服务不同目标。Undo 保存修改前信息，用于回滚和 MVCC；Redo 是 InnoDB 的 WAL 恢复日志，让数据页不必每次提交都同步随机刷盘；Binlog 属于 Server 层，记录事务事件，用于复制、CDC 和时间点恢复。一次写入会修改内存页并产生这些日志，但日志不能防止业务误操作，所以生产仍需要备份、Binlog 保留、恢复演练和对账。”

### ⑨ 追问
- Redo 为什么更接近物理日志，Binlog 为什么更偏逻辑事件？
- Undo 何时才能被 Purge 清理？

> **记忆句**：Undo 撤销，Redo 恢复，Binlog 复制。

## Q24. MySQL 为什么需要 Redo 和 Binlog 的两阶段提交？

> **题型**：资深原理题｜**实际难度**：中等偏上｜**频率**：★★★★★

### ① 为什么现在学
本地事务同时涉及 InnoDB Redo 与 Server Binlog，必须让两者对“这笔事务是否提交”得到一致结论。

### ② 具体画面
如果 Redo 显示事务已提交而 Binlog 缺失，主库恢复后有数据，但副本和增量恢复不知道这笔事务。

### ③ 问题来源

```text
只有 Redo 成功、Binlog 失败
  → 主库恢复有事务，副本没有

只有 Binlog 成功、Redo 未提交
  → 副本可能重放主库最终不存在的事务
```

### ④ 提交流程心智图

```text
InnoDB 写 Redo Prepare
→ Server 写/刷 Binlog
→ InnoDB 写 Redo Commit
→ 返回客户端
```

崩溃恢复时，Prepare 状态事务可结合 Binlog 是否存在完整提交记录决定提交或回滚。

### ⑤ 企业级边界
这里的两阶段提交是 MySQL 内部 Redo 与 Binlog 协调，不会自动把 Redis、RocketMQ、Milvus 或外部 Tool 纳入一个全局事务。跨系统要使用 Outbox、Inbox、Saga、幂等与对账。

### ⑥ 最小案例
完成 Run 的事务同时更新 `agent_run` 并插入 `outbox_event`。这两个表由 MySQL 本地事务保证；Outbox 发布到 RocketMQ 是后续可重试过程。

### ⑦ 小结
> 两阶段提交让 Redo 与 Binlog 对同一事务的提交结论一致。

### ⑧ 2～3 分钟口述
“MySQL 需要协调 InnoDB Redo 和 Server Binlog。如果只写 Redo，主库恢复后可能有事务，但副本和增量恢复没有；如果只有 Binlog，副本可能重放主库最终没有提交的数据。典型流程是 Redo Prepare、写 Binlog、Redo Commit。宕机恢复时可根据 Binlog 完整性决定 Prepare 事务提交还是回滚。这个机制只保证 MySQL 内部日志一致，不等于 MySQL 与 RocketMQ 的全局两阶段事务。”

### ⑨ 追问
- Redo Prepare 状态的作用是什么？
- `sync_binlog` 与 `innodb_flush_log_at_trx_commit` 如何影响故障窗口？

> **记忆句**：Redo 与 Binlog 必须共同证明一次提交完整。

## Q25. MySQL 崩溃恢复的大致流程是什么？

> **题型**：资深恢复题｜**实际难度**：中等偏上｜**频率**：★★★★☆

### ① 为什么现在学
把日志串成断电后的恢复时间线，而不是只背术语。

### ② 具体画面
事务已经向客户端返回成功，但部分脏页还在内存；机器断电后，MySQL 要用 Redo 让数据页追上已提交状态。

### ③ 恢复主线

```text
启动读取数据文件和检查点
→ 扫描检查点后的 Redo
→ 重做应存在的页修改
→ 识别未完成事务
→ 利用 Undo 回滚未提交事务
→ 处理 Redo Prepare 与 Binlog 协调
→ 完成恢复并开放服务
```

### ④ 深入原理
WAL 允许提交先保证顺序日志持久，再由后台刷随机脏页。检查点记录数据页推进到哪个 LSN，限制需要扫描的 Redo 范围。恢复完成时间与 Redo 量、脏页、磁盘和未完成事务有关。

### ⑤ 企业级边界
高可用不仅看能否恢复，还要定义 RPO/RTO、Redo 容量、启动恢复时长、备份恢复、Binlog 回放、主从切换与业务对账。单机 Crash Recovery 不能替代跨机灾备。

### ⑥ 最小案例
Run 终态事务已提交、脏页未刷盘时宕机：启动后 Redo 重做 SUCCEEDED；另一个未提交事务由 Undo 回滚。

### ⑦ 小结
> 提交先保证日志，页可稍后刷；崩溃后用 Redo 重做、Undo 回滚。

### ⑧ 2～3 分钟口述
“InnoDB 使用 WAL，事务提交不要求所有数据页立即刷盘。崩溃启动时，MySQL 从检查点附近扫描 Redo，把应存在但数据页尚未持久化的修改重做；未提交事务再利用 Undo 回滚。处于 Redo Prepare 的事务还要结合 Binlog 判断提交还是回滚。生产还需关注恢复时长、Redo 容量、磁盘吞吐、长事务和备份恢复，因为单机恢复不等于跨机容灾。”

### ⑨ 追问
- 检查点怎样限制恢复范围？
- Redo 过小或刷脏跟不上会发生什么？

> **记忆句**：Redo 重做已提交，Undo 清理未完成。

## Q26. MySQL 主从复制的基本链路是什么？

> **题型**：高频架构题｜**实际难度**：中等｜**频率**：★★★★★

### ① 为什么现在学
从主库提交到副本重放建立复制第一张图。

### ② 具体画面
主库不是把数据文件实时拷贝给副本，而是把 Binlog 事务流交给副本拉取和重放。

### ③ 复制主线

```text
客户端事务在 Source 提交
→ 写入 Binlog
→ Replica I/O Receiver 拉取事件
→ 写入 Relay Log
→ SQL/Applier Thread 重放事务
→ 副本数据逐步追上
```

### ④ 深入原理
副本的接收与应用是解耦的：网络能及时拉到 Relay Log，不代表事务已经应用完成。并行复制可按事务依赖并发应用，但热点行、长事务和 DDL 仍可能成为瓶颈。

### ⑤ 企业级边界
复制通常存在延迟。必须监控接收位置、应用位置、Seconds_Behind_Source 的局限、Relay Log、Applier Worker、最老未应用事务和错误。读副本适合可接受陈旧的读，不应默认承担读己之写。

### ⑥ 最小案例
主库写 Run=SUCCEEDED，副本已接收 Binlog 但尚未应用；立即从副本读取仍可能看到 RUNNING。

### ⑦ 小结
> 复制 = 主库产生 Binlog，副本拉取 Relay Log 并重放。

### ⑧ 2～3 分钟口述
“MySQL 复制以 Binlog 为事务流。主库提交后产生 Binlog，副本 I/O Receiver 拉取并写入 Relay Log，Applier 再按顺序或并行重放。接收完成不等于应用完成，所以会存在复制延迟。生产要分别监控网络接收、Relay Log 积压、Applier Worker、长事务和错误，不能只看一个 Seconds_Behind 指标。”

### ⑨ 追问
- 并行复制按什么条件并发应用？
- 大事务为什么容易造成复制延迟？

> **记忆句**：Binlog 产生事务流，副本拉取、落 Relay Log、再重放。

## Q27. GTID 有什么作用？异步复制与半同步复制有什么差异？

> **题型**：资深高可用题｜**实际难度**：中等偏上｜**频率**：★★★★☆

### ① 为什么现在学
在复制主链上加入事务身份、自动定位和确认强度。

### ② 具体画面
GTID 像事务的全局快递单号；副本能明确知道自己执行过哪些、缺少哪些事务。

### ③ GTID
GTID 为写入 Binlog 的事务分配全局唯一身份，通常形如 `server_uuid:sequence_number`。它支持自动定位、比较执行集合、等待某事务和简化故障切换。

### ④ 异步与半同步

```text
异步复制
  主库提交后不等待副本确认
  延迟低，但主库故障时确认事务可能尚未到副本

半同步复制
  主库在返回前等待至少一个副本达到配置的确认点
  缩小丢失窗口，但增加延迟并受超时/降级策略影响
```

半同步的确认不必等同于副本业务 SQL 已完全应用，需要明确版本和配置。

### ⑤ 企业级边界
GTID 简化事务定位，不自动选择正确新主，也不防止旧主双写。半同步提高确认强度，不等于共识协议或零数据丢失。仍需 Fencing、只读控制、拓扑管理和对账。

### ⑥ 最小案例
完成 Run 后记录本次会话 GTID；强一致读可回主或等待目标副本执行该 GTID，再读取。

### ⑦ 小结
> GTID 标识事务，半同步加强确认，但高可用仍需切换协议。

### ⑧ 2～3 分钟口述
“GTID 给每个写入 Binlog 的事务一个全局唯一标识，副本可以比较执行集合并自动定位缺失事务，故障切换和等待特定事务更方便。异步复制不等待副本，延迟低但故障窗口更大；半同步在返回前等待至少一个副本达到确认点，缩小丢失窗口但增加延迟。GTID 和半同步都不等于零丢失，也不能自动防止旧主恢复后继续写。”

### ⑨ 追问
- GTID auto-position 的核心依据是什么？
- 半同步 ACK 到哪一步？该确认是否代表事务已可读？

> **记忆句**：GTID 管事务身份，半同步管返回前确认强度。

## Q28. 写主读从为什么会读不到刚写的数据？怎样解决？

> **题型**：高频一致性题｜**实际难度**：中等偏上｜**频率**：★★★★★

### ① 为什么现在学
理解复制延迟后，读写分离的一致性问题自然出现。

### ② 具体画面
接口刚把 Run 写成 SUCCEEDED，下一次请求路由到尚未重放该事务的副本，读到 RUNNING。

### ③ 原因

```text
主库已提交并返回
→ Binlog 传输/Relay Log
→ 副本等待或重放
→ 读取发生在副本应用完成之前
```

延迟来源包括网络、长事务、单线程热点、磁盘、DDL、锁和副本资源不足。

### ④ 解决方案
按业务一致性需求选择：

- 写后短时间粘滞主库；
- 关键状态始终读主；
- 携带 GTID，等待副本执行后再读；
- 业务版本/状态判断，旧版本则回主；
- 可接受陈旧的列表和统计继续读从；
- 控制副本延迟阈值，超阈值摘除。

### ⑤ 企业级边界
不能把所有读强制回主，否则失去读扩展；也不能所有读从，否则支付、权限、任务终态可能错误。接口需定义一致性等级。

### ⑥ 最小案例
`POST /runs/{id}/finish` 返回版本 18；后续 GET 若从副本读到 version<18，则等待 GTID或回主。

### ⑦ 小结
> 副本延迟会破坏读己之写，关键读需等待、粘主或版本回退。

### ⑧ 2～3 分钟口述
“写主读从读不到刚写数据，本质是 Binlog 已在主库提交，但副本还在传输或重放。解决不是简单关闭读写分离，而是按业务分级：终态、权限和写后确认读主或等待 GTID；普通列表允许短暂陈旧；也可返回业务 version，副本版本不足时回主。还要监控副本应用延迟并在超过阈值时摘除。”

### ⑨ 追问
- 如何实现 Session 粘滞读？
- 等待 GTID 超时后怎样降级？

> **记忆句**：写后读要知道目标版本，副本不足就等待或回主。

## Q29. 主库故障后，怎样完成安全切换并保证业务可恢复？

> **题型**：项目深挖题｜**实际难度**：困难｜**频率**：★★★★☆

### ① 为什么现在学
把复制、GTID、流量切换、幂等和对账组合成真实故障演练。

### ② 具体画面
主库失联后不能只挑一台副本提升；还要防止旧主恢复继续写，并确认新主缺少哪些事务。

### ③ 安全切换主线

```text
检测主库不可用
→ 停止/隔离旧主写入（Fencing）
→ 收敛应用重试与入口流量
→ 比较候选副本 GTID、延迟和健康状态
→ 选择最完整且可用的副本
→ 提升为新主并重建复制拓扑
→ 更新 Router/DNS/配置并灰度切流
→ 检查只读、连接池和旧主隔离
→ 对账最后事务与业务状态
→ 处理旧主重新加入
```

### ④ 深入原理
GTID 集合帮助比较事务完整度，但选择新主还需考虑副本错误、数据一致性、硬件和恢复时间。旧主必须被网络、权限、STONITH 或数据库只读策略隔离，避免双主写入。

### ⑤ 企业级边界
故障期间客户端会遇到连接中断、提交结果未知和重试。所有写接口要有 requestId/operationId；Outbox 与业务表同事务；恢复后检查重复、缺失、状态倒退和消息积压。

### ⑥ 演练验收

```text
随机强杀主库
→ 制造复制延迟
→ 切换期间重复请求
→ 验证只有一个可写主库
→ 已确认事务不静默丢失或能被对账发现
→ Tool/支付等副作用不重复
→ MQ 可继续消费
```

### ⑦ 小结
> 故障切换 = 隔离旧主 + 选最完整副本 + 切流 + 业务对账。

### ⑧ 2～3 分钟口述
“主库故障后第一步不是立即提升副本，而是隔离旧主，防止它恢复后继续写。然后收敛应用重试，比较候选副本 GTID 集合、复制延迟和健康状态，选择最完整副本提升，重建拓扑并通过 Router 或配置灰度切流。切换期间可能出现提交结果未知，所以写接口必须有 operationId，Outbox 与业务状态同事务。恢复后还要对账最后事务、重复请求、状态机、消息积压，并演练旧主重新加入。”

### ⑨ 追问
- 怎样防止旧主恢复后形成双主？
- 客户端超时但事务可能已提交时怎样处理？

> **记忆句**：先隔离，再选主；切流之后必须对账。

## Q30. MySQL 什么时候需要分库分表？

> **题型**：高频架构题｜**实际难度**：中等｜**频率**：★★★★★

### ① 为什么现在学
只有单机容量或写入瓶颈被证据证明后，才进入分片。

### ② 具体画面
单表达到一亿行不一定立刻分片；如果核心查询只访问窄索引范围、冷热数据已归档，单机可能仍可承受。

### ③ 判断维度

```text
容量：数据、索引、备份、恢复和 DDL 窗口是否不可持续
吞吐：单主写入、Redo、锁和 CPU 是否接近稳定上限
可用性：故障域和维护窗口是否无法满足
增长：未来 6～12 个月是否必然突破上限
```

### ④ 分片前的治理顺序

```text
修慢 SQL 与索引
→ 拆大字段、冷热分离和归档
→ 扩大 Buffer Pool / 升级硬件
→ 读写分离和缓存
→ 拆服务与业务边界
→ 最后分片
```

### ⑤ 企业级边界
分片会失去或弱化单库事务、Join、唯一约束、排序分页、外键、全局统计和简单运维。团队必须有路由、迁移、对账、容量和故障工具。

### ⑥ 最小案例
NexusAgent 的 `agent_message` 增长最快，可先按时间归档和冷热表；`agent_run` 核心状态仍保持单库。只有写吞吐与容量证据证明不可持续时，再按 tenant 或一致性哈希分片。

### ⑦ 小结
> 分片是最后的容量手段，不是慢 SQL 的第一答案。

### ⑧ 2～3 分钟口述
“我不会以单表行数作为唯一分片阈值，而会看数据与索引容量、备份恢复时间、DDL 窗口、单主写吞吐、锁与 Redo、未来增长和故障域。分片前先治理 SQL、索引、大字段、归档、缓存、读副本和硬件。因为分片会带来跨片事务、Join、排序、唯一约束和迁移复杂度。NexusAgent 可以先归档消息和 Trace，只有单实例写入或容量被证据证明无法持续时才分片。”

### ⑨ 追问
- 分片前还能做哪些单机治理？
- 如何量化单库的安全容量线？

> **记忆句**：先把单库用对，再决定是否拆开。

## Q31. MySQL 分区表和分库分表有什么区别？

> **题型**：对比题｜**实际难度**：中等｜**频率**：★★★★☆

### ① 为什么现在学
分区仍在一个实例，分片跨多个实例；两者解决的层级不同。

### ② 具体画面
按月分区的消息表仍由同一个 MySQL 实例处理 CPU、Redo 和锁；分片则把不同数据路由到不同实例。

### ③ 标准区别

```text
分区表
  一张逻辑表、一个实例
  数据按分区规则存放
  可用于分区裁剪、生命周期管理和维护
  不能突破单实例 CPU、内存、Redo 和故障域

分库分表
  多个实例/物理表
  应用或中间件路由
  可水平扩展容量与写入
  引入跨片事务、Join、排序和迁移难题
```

### ④ 深入原理
分区裁剪要求查询条件能够推导目标分区。若条件不含分区键或表达式不可裁剪，仍可能访问多个分区。分区主键和唯一键还受分区键约束。

### ⑤ 企业级边界
时间序列、日志和归档表适合按时间分区，但高并发 OLTP 热点写不一定因分区而消失。分片用于跨实例扩展，但必须先定义路由和一致性边界。

### ⑥ 最小案例
`agent_message` 按月分区方便删除历史分区；如果单实例写入已饱和，仍需按 tenant/run 进一步分片或迁移到专用存储。

### ⑦ 小结
> 分区优化单实例内组织，分片改变跨实例架构。

### ⑧ 2～3 分钟口述
“分区表仍是一张逻辑表和一个 MySQL 实例，只是数据按规则进入不同分区，适合分区裁剪和按时间维护；它不能突破单实例 CPU、Redo、内存和故障域。分库分表把数据路由到多个实例，能扩展容量和写吞吐，但会削弱单库事务、Join、唯一约束和排序分页。Agent 消息可先按月分区归档，只有单实例资源成为瓶颈时再分片。”

### ⑨ 追问
- 分区裁剪失效时会发生什么？
- 分区键为什么影响唯一索引设计？

> **记忆句**：分区是单实例内组织，分片是跨实例路由。

## Q32. 分片键、路由表和全局 ID 应怎样设计？

> **题型**：资深架构题｜**实际难度**：中等偏上｜**频率**：★★★★☆

### ① 为什么现在学
分片系统先决定数据去哪，再考虑 ID、扩容和热点。

### ② 具体画面
按 tenant 分片能让租户数据局部化，但超级租户可能成为热点；按 runId 分片更均匀，却让租户列表跨片。

### ③ 分片键选择
评估：

```text
查询局部性
事务局部性
数据与 QPS 均匀性
超级租户/热点风险
扩容迁移成本
合规与租户隔离
```

常见策略：tenantId、业务 ID 哈希、范围、目录路由、一致性哈希或组合策略。

### ④ 路由表
目录路由保存 `tenant_id → shard_id`，便于大租户独立迁移，但路由本身要高可用、缓存可失效、版本化并可审计。迁移期间通常经历复制、双读/校验、切换和清理，而不是长期无条件双写。

### ⑤ 全局 ID
可使用号段、Snowflake 类 ID、UUID/ULID 等。ID 需考虑唯一性、趋势性、时钟回拨、信息泄露、索引宽度和生成服务可用性。业务唯一性仍应由业务唯一键表达，不能只依赖全局主键。

### ⑥ 最小案例
普通 tenant 按哈希分片；超级 tenant 通过路由表迁入独立 shard；Run ID 使用趋势递增的 64 位 ID，但 `(tenant_id, operation_id)` 继续保证工具幂等。

### ⑦ 小结
> 分片键决定局部性和热点，路由表决定可迁移性，全局 ID 只解决身份。

### ⑧ 2～3 分钟口述
“分片键要同时考虑查询和事务局部性、数据/QPS 均匀性、超级租户、扩容和合规。按 tenant 可让租户内查询局部化，但大租户会热点；按 runId 更均匀，却让租户列表跨片。因此可采用普通租户哈希加超级租户目录路由。全局 ID 选择还要考虑趋势性、时钟和索引宽度，但业务幂等仍由 tenant_id + operation_id 这样的唯一约束保证。”

### ⑨ 追问
- 扩容迁移期间怎样保证数据一致？
- 路由缓存与数据库路由版本不一致怎么办？

> **记忆句**：分片键决定去哪，路由表决定怎么搬，ID 决定是谁。

## Q33. 跨分片事务、Join、排序和分页怎样处理？

> **题型**：资深系统设计题｜**实际难度**：困难｜**频率**：★★★★☆

### ① 为什么现在学
分片后的难点不是路由本身，而是单库能力被削弱。

### ② 具体画面
查询一个租户跨多个 shard 的全部 Run 并按时间全局排序，不能再由一个 MySQL 自然完成。

### ③ 跨片事务
优先重构为单分片本地事务；跨片流程使用 Saga、Outbox、幂等和补偿。XA 只在极少数边界明确、资源受控的场景评估，不能用来覆盖分钟级外部调用。

### ④ 跨片 Join
可通过数据冗余、读模型、搜索/分析系统、应用批量查询或维度表广播解决。禁止逐行 N+1 跨片请求。

### ⑤ 全局排序分页
各 shard 按相同排序键取 Top K，由聚合层归并；使用复合游标携带每个 shard 位置或稳定时间窗口。深 OFFSET 会让所有 shard 扫描并丢弃大量数据。

### ⑥ 唯一性与计数
全局唯一业务键可由集中目录、唯一性服务或基于分片键的约束解决。全局 COUNT/聚合可用异步汇总和分析库，避免每次在线 fan-out 全部 shard。

### ⑦ 小结
> 分片后要用业务重构恢复需要的能力，而不是假装仍是一个数据库。

### ⑧ 2～3 分钟口述
“跨片后我优先让事务和核心查询局部化。必须跨片的业务用 Saga、Outbox、幂等和补偿，不把长外部调用放入 XA。Join 通过冗余读模型、批量查询或搜索分析系统解决；全局排序由各 shard 取 Top K 后归并，分页使用稳定复合游标，避免全局深 OFFSET。全局唯一和统计需要目录或汇总服务。分片带来的本质代价是单库原子性和查询能力下降。”

### ⑨ 追问
- 跨片分页如何避免全量归并？
- Saga 补偿失败怎样处理？

> **记忆句**：跨片能力要在业务层重构。

## Q34. 企业级 Agent/RAG 平台的 MySQL 表应该怎样设计？

> **题型**：项目深挖题｜**实际难度**：中等偏上｜**频率**：★★★★★

### ① 为什么现在学
把全书知识组合成表、约束、状态机、Outbox 和冷热分层。

### ② 业务不变量

```text
租户不能串数据
一个 Run 状态不能倒退
一个 Tool Operation 不能重复执行
同一 Run 的消息序号不能重复
终态与事件能够恢复和对账
```

### ③ 表设计

```text
agent_run        热状态、owner、version、时间
agent_message    tenant+run+seq 唯一，正文按序读取
tool_operation   tenant+operation_id 唯一，记录副作用状态
outbox_event     与业务状态同事务写入
run_event        追加审计事件，可重放状态演进
object_ref       大 Prompt/Trace 的 URI、digest、size、version
```

### ④ 索引与约束
所有租户查询和唯一约束显式包含 tenant_id；列表索引匹配 tenant/status/time/id；消息使用 `(tenant_id,run_id,seq_no)`；幂等使用 `(tenant_id,operation_id)`；Outbox 使用稳定 event_id。

### ⑤ 状态机与事务
认领和完成使用条件 UPDATE；外部调用在事务外；结果回写校验 owner/version；状态更新和 Outbox 同事务；消费者使用 Inbox/唯一键折叠重复。

### ⑥ 数据生命周期
热 Run 与大正文拆表；Trace 和附件进对象存储；历史消息归档/分区；PII 加密脱敏；版本化 Schema；提供删除和审计流程。

### ⑦ 小结
> 表结构必须表达租户边界、状态机、幂等、事件事实和恢复路径。

### ⑧ 2～3 分钟口述
“我会把 Agent 平台拆成 Run 热状态、消息正文、Tool Operation、Outbox、审计事件和对象引用。所有核心索引包含 tenant_id；消息用 tenant+run+seq 唯一，Tool 用 tenant+operation_id 幂等。Run 认领和完成使用 status+version 条件 UPDATE，远程调用在事务外，状态与 Outbox 同事务。大 Prompt 和 Trace 放对象存储，MySQL 保存摘要和状态。这样既支持列表性能，也支持消息重试、故障恢复和业务对账。”

### ⑨ 追问
- Outbox 表为什么需要唯一 event_id？
- 状态事件表与当前状态表为什么可以同时存在？

> **记忆句**：主表存当前事实，事件表存演进，操作表存幂等。

## Q35. MySQL 接口 P99 突然升高，你会怎样定位？

> **题型**：项目终极深挖题｜**实际难度**：困难｜**频率**：★★★★★

### ① 为什么现在学
训练大厂最看重的跨层排障能力：应用、SQL、锁、I/O、日志和复制。

### ② 第一原则：先分段

```text
请求总耗时
= 线程/队列等待
+ 连接池等待
+ 网络
+ MySQL 排队/执行
+ 锁等待
+ 结果传输
+ Java 解码与 GC
```

### ③ 现场止血
限制失控接口并发与结果大小；暂停批处理和低优先级消费者；关闭多层无限重试；设置总 Deadline；保护主库连接；必要时降级读副本或非核心功能。

### ④ 证据链
应用侧看 Hikari active/pending、pool_wait、SQL digest、Trace、GC；MySQL 看 Threads_running、QPS、Slow Log、Performance Schema digest、锁等待、Buffer Pool、磁盘、Redo、脏页、临时表；复制看 Relay Log 和 Applier 延迟。

### ⑤ 常见事故链

```text
大租户深分页/SELECT *
→ 扫描、回表和大结果
→ 连接持有时间增加
→ 池等待
→ Worker 状态更新变慢
→ 消费 TPS 下降
→ MQ Lag 上升
→ 重试进一步放大
```

也可能是长事务阻塞 DDL/锁、统计改变导致计划回归、存储抖动、Redo 刷盘、备份或副本延迟。

### ⑥ 修复闭环
先用真实参数复现；比较 estimated/actual rows；修 SQL、索引、分页、数据模型或容量；灰度；混合读写回放；观察查询和写入 P99、副本延迟、索引空间；准备回退。

### ⑦ 小结
> P99 排查必须从端到端时间线和跨组件证据开始。

### ⑧ 2～3 分钟口述
“我先把 P99 分成连接池等待、SQL 执行、锁、网络和结果解码，并立即限制失控接口、批处理和多层重试。应用侧看 Hikari pending、Trace 和 result bytes；MySQL 看 Threads_running、digest、Slow Log、data_lock_waits、Buffer Pool、磁盘、Redo 和临时表；副本看应用延迟。定位后用真实参数和 EXPLAIN ANALYZE验证。常见根因是深分页、SELECT *、计划回归、锁等待或存储抖动。修复必须灰度、回放并同时观察读 P99、写放大和 MQ Lag。”

### ⑨ 追问
- 如何区分锁等待与 I/O 抖动？
- 数据库指标正常但接口仍慢怎么办？

> **记忆句**：先分段，再找证据；不要看到超时就先加连接。

## Q36. 如何为 Agent 平台设计 MySQL 安全、容量和无损 Schema 演进？

> **题型**：资深治理题｜**实际难度**：困难｜**频率**：★★★★☆

### ① 为什么现在学
把安全、容量、DDL 和回滚计划组合成长期治理能力。

### ② 安全基线
最小权限账号；读写和迁移账号分离；TLS；凭据轮换；按 tenant 强制过滤；敏感列加密或 Token 化；审计高风险 SQL；备份加密；禁止应用拥有 DROP/ALTER 等超额权限。

### ③ 容量模型

```text
业务行与索引
+ Buffer Pool 外内存
+ Redo/Undo/Binlog
+ 临时表与排序
+ 备份/恢复空间
+ 在线 DDL 临时空间
+ 副本和增长余量
```

按租户、表、索引、写入字节、保留周期和增长率预测；同时定义 RPO/RTO 和恢复时长。

### ④ Schema 演进
采用 Expand-Migrate-Contract：

```text
先增加兼容新列/新表
→ 应用双读或受控双写
→ 后台回填并校验
→ 切换读路径
→ 观察一段时间
→ 删除旧字段/旧索引
```

避免一步破坏性修改。在线 DDL 仍可能等待 MDL，并消耗磁盘、Redo 和副本应用能力。

### ⑤ 无损要求
回填分批限速、可暂停和断点续跑；每批带范围和校验；新旧版本可并存；写入幂等；变更前检查长事务和空间；提供回滚开关；监控副本延迟、MDL、磁盘、错误率和数据差异。

### ⑥ 最小案例
把 `status VARCHAR` 演进为状态码：先新增 `status_code`，新应用双写；后台按主键范围回填；校验计数与抽样；读路径切到新列；稳定后再停止旧列写入并最终删除。

### ⑦ 小结
> Schema 演进要兼容、可观测、可暂停、可校验、可回滚。

### ⑧ 2～3 分钟口述
“Agent 平台的 MySQL 治理分安全、容量和变更三部分。安全上使用最小权限、TLS、凭据轮换、租户条件、敏感字段保护和审计；容量不仅看表数据，还看索引、Redo、Undo、Binlog、临时空间、在线 DDL 和恢复时间。Schema 采用 Expand-Migrate-Contract：先兼容扩展，再限速回填和校验，切换读路径，最后收缩旧结构。上线前检查长事务、MDL、磁盘和副本延迟，整个过程可暂停、断点续跑和回滚。”

### ⑨ 追问
- Online DDL 为什么仍可能被 MDL 阻塞？
- 如何验证回填没有漏行、重复或业务语义变化？

> **记忆句**：安全靠最小权限，容量靠完整模型，变更靠兼容与回滚。

# Redis 8.8 面试题 Q02

## Q02. 数据类型、内部编码与 Key 设计有什么关系

**类型：高频基础题＋项目设计题｜难度：简单偏中等｜重要性：★★★★★**

### ① 先分清三个层次

初学者容易把“Hash”“哈希表”“Key”混在一起。

```text
Key      → 这份数据叫什么
Type     → 业务上允许怎样操作
Encoding → Redis 内部具体怎样存
```

例子：

```text
Key      = nexus:run:{T1:R1}:meta
Type     = Hash
Encoding = 小对象可能使用紧凑结构，变大后可能转换
```

### ② 类型回答“业务怎样访问”

| 访问方式 | 优先考虑 |
|---|---|
| 整体读取、覆盖、计数 | String |
| 按字段读写对象 | Hash |
| 两端添加、顺序记录 | List |
| 去重和成员判断 | Set |
| 按分数排序、范围查询 | ZSet |
| 消费组、ACK、重投 | Stream |

选择类型时，先问：

```text
我最常执行什么操作？
```

而不是问：

```text
哪个类型听起来最高级？
```

### ③ 内部编码回答“怎样更省空间或更适合增长”

同一个逻辑类型，Redis 可以根据对象大小选择不同内部结构。

只需建立直觉：

```text
小对象
  → 更紧凑，减少指针和内存分配

对象变大
  → 转换成更适合查找、更新或排序的通用结构
```

常见心智模型：

- String：整数、小字符串、普通字符串；
- Hash：小型紧凑结构或哈希表；
- List：由多个紧凑节点组成的双向结构；
- Set：整数集合、紧凑集合或哈希表；
- ZSet：小型紧凑结构，或“字典 + 跳表”；
- Stream：有序索引组织紧凑消息块，并维护消费组状态。

面试不应把易变的转换阈值背成永远不变的常量。

### ④ Key 应怎样设计

推荐格式：

```text
应用:资源:{最小原子业务单元}:子资源:版本
```

例如：

```text
nexus:run:{T1:R1}:meta
nexus:run:{T1:R1}:tool-result:search
nexus:retrieval:{T1:KB17}:v8:query:a913
```

Key 至少表达：

1. 业务域；
2. 租户；
3. 资源类型；
4. 业务 ID；
5. 必要版本。

### ⑤ 为什么不能把一个租户全部放到同一个 Hash Tag

```text
nexus:{tenant:T1}:所有数据
```

虽然这些 Key 会进入同一 Cluster Slot，方便多 Key 操作，但也可能让大租户全部压到同一节点，形成 Hot Slot。

Hash Tag 应覆盖**真正需要一起原子操作的最小范围**，例如一个 Run，而不是整个租户。

### ⑥ 一个完整选型示例

需求：保存 Agent Run 的状态、所有者、版本和更新时间。

访问特点：

```text
经常只修改 status
经常只读取 status + version
字段数量固定且很少
```

所以使用小 Hash 比大 JSON String 更自然。

### ❌ 容易制造事故的写法

```java
String key = "tenant:1:all";
// 把整个租户所有 Run、消息和工具结果放进一个 JSON。
redis.set(key, hugeTenantJson);
```

### ✅ 企业级改进示例

```java
String metaKey = "nexus:run:{%s:%s}:meta".formatted(tenantId, runId);
redis.hset(metaKey, Map.of(
        "status", status,
        "owner", owner,
        "version", Long.toString(version)));
redis.expire(metaKey, Duration.ofHours(2));
```

### 🎙️ 2～3 分钟优秀回答

我会把 Key、数据类型和内部编码分成三层。Key 解决业务身份问题，数据类型解决客户端可见的操作语义，内部编码解决 Redis 实际存储成本。

例如 Agent Run 元数据的 Key 可以是 `nexus:run:{T1:R1}:meta`，逻辑类型选择 Hash，因为业务经常按字段读取和修改。Redis 内部可能对小 Hash 使用紧凑编码，变大后转换成哈希表。转换后 API 不变，但内存和操作成本会变化。

类型选择应从访问模式出发：整体值和计数用 String，字段对象用 Hash，去重用 Set，排序用 ZSet，需要消费组与 ACK 才考虑 Stream。Key 通常包含应用、租户、资源、业务 ID 和版本。Cluster 的 Hash Tag 只覆盖最小原子业务单元，不能把整个大租户固定在一个 Slot。

因此我的选型顺序是：先确定业务访问方式，再选 Type，再控制大小和 TTL，最后才关注 Encoding。

### 面试官可能继续追问

- Hash 什么时候可能从紧凑编码转换？
- 为什么 ZSet 的通用实现需要字典和跳表两种结构？

> **记忆句**：Key 定身份，Type 定语义，Encoding 定成本，TTL 定生命周期。

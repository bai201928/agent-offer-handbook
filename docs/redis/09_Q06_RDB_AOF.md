# Redis 8.8 面试题 Q06

## Q06. RDB、AOF 与混合持久化怎样选择

**类型：高频基础题｜难度：简单偏中等｜重要性：★★★★★**

### ① 先回答为什么需要持久化

Redis 数据主要在内存中。进程退出或机器重启后，内存数据会消失。

持久化是在磁盘上准备恢复材料。

### ② RDB：拍一张快照

```text
10:00 给整个仓库拍照
10:05 机器故障
```

恢复时最多只能回到 10:00 的状态，10:00～10:05 的变化可能丢失。

优点：

- 文件紧凑；
- 适合备份；
- 加载通常较快。

缺点：

- 两次快照之间存在数据窗口；
- 生成快照涉及 fork；
- 大数据集会增加磁盘和内存压力。

### ③ AOF：记录写操作流水

例如：

```text
SET a 1
INCR counter
DEL old-key
```

恢复时重放这些操作。

AOF 的 `fsync` 策略决定数据窗口与性能权衡。

优点：

- 通常可获得更小的数据丢失窗口；
- 操作历史更连续。

缺点：

- 文件和写放大更大；
- 需要重写；
- 恢复时间和磁盘性能要评估。

### ④ 混合持久化

AOF 重写后，前部可使用更适合快速加载的快照形式，尾部记录增量写，兼顾加载速度与较小数据窗口。

### ⑤ 选择前先问 RPO 和 RTO

```text
RPO：最多允许丢多少数据
RTO：故障后多久必须恢复
```

还要问：

```text
数据能否从 MySQL、Milvus 或对象存储重建？
```

纯缓存与幂等记录不能用同一套答案。

### ⑥ 持久化不等于备份，也不等于业务正确

误执行删除命令，错误也可能进入 AOF 和副本。

Redis 持久化无法解决：

- 业务误删；
- 权限事故；
- MySQL 与 Redis 双写不一致；
- 外部 Tool 已执行但 Redis 状态没写。

仍需独立备份、事实源、审计和对账。

### ❌ 容易制造事故的写法

```java
// 把支付事实只写入 Redis，并认为开启 AOF 就等于金融级可靠。
redis.set("payment:" + orderId, "SUCCESS");
```

### ✅ 企业级改进示例

```java
@Transactional
public void confirmPayment(Payment payment) {
    paymentRepository.save(payment);          // MySQL 是事实源
    outboxRepository.save(PaymentEvent.of(payment));
    // Redis 仅保存可重建的查询视图或短期状态。
}
```

### 🎙️ 2～3 分钟优秀回答

RDB 是某一时刻的数据快照，文件紧凑、恢复通常较快，但两次快照之间的写可能丢失。AOF 记录写命令并在启动时重放，通常可以提供更小的数据窗口，但有额外写放大、重写和恢复成本。混合持久化希望兼顾快照加载速度和增量写记录。

生产选型不能只问哪个更安全，而要先为不同状态定义 RPO、RTO 和重建来源。纯检索缓存可以无持久化并从 MySQL 或 Milvus 重建；Session 可接受小窗口；幂等记录、租约或热 Checkpoint 应隔离并有权威记录。

我还会评估 fork、COW、磁盘、AOF fsync、恢复演练和独立备份。持久化只能帮助 Redis 自身重启恢复，不解决业务误删和跨系统一致性。

### 面试官可能继续追问

- AOF everysec 是否保证绝对不丢 1 秒数据？
- 为什么开启持久化仍要做独立备份？

> **记忆句**：RDB 是照片，AOF 是流水账；选型先看 RPO、RTO 和事实源。

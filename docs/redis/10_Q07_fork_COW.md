# Redis 8.8 面试题 Q07

## Q07. fork 与 COW 为什么会造成内存和延迟峰值

**类型：资深工程师追问题｜难度：中等偏上｜重要性：★★★★☆**

### ① 先理解 fork 做了什么

Redis 需要生成 RDB 或执行部分 AOF 重写时，会创建子进程。

初始时，父子进程看起来拥有同一份内存，但操作系统不会立刻复制全部数据，而是让它们共享物理页。

### ② 什么是 COW

COW 是 Copy-On-Write，写时复制。

```text
父进程和子进程都只读某页
  → 继续共享

父进程要修改某页
  → 操作系统复制该页
  → 父进程写新页
  → 子进程继续看旧页
```

这样子进程看到快照时刻的数据，父进程仍能服务新请求。

### ③ 为什么产生内存峰值

如果后台快照期间写入很多：

```text
大量旧页需要保留给子进程
+ 父进程修改后产生新页
```

RSS 会升高。

风险取决于：

- 数据集大小；
- 写入速率；
- 子进程运行时间；
- 磁盘速度；
- 内存碎片；
- 大页；
- 容器内存限制。

### ④ 为什么产生延迟

- fork 建立页表需要时间；
- 操作系统复制内存页；
- 子进程大量读内存和写磁盘；
- 磁盘与 CPU 竞争；
- 宿主机或容器接近内存上限。

### ⑤ 为什么 maxmemory 不能等于容器内存上限

Redis 除了数据集，还需要：

```text
COW 峰值
复制缓冲
AOF 缓冲
客户端输入/输出缓冲
allocator 和碎片
模块内存
系统空间
```

如果容器限制 16GB，把 `maxmemory` 也设置成 16GB，后台任务期间很容易被 OOM Kill。

### ⑥ 应监控什么

- `latest_fork_usec`；
- 后台保存/重写状态；
- `used_memory`；
- `used_memory_rss`；
- COW 指标；
- 容器 Working Set；
- 磁盘吞吐和延迟；
- OOM 与重启。

### ❌ 容易制造事故的写法

```java
# 容器限制 16GB
maxmemory 16gb
# 没有为 COW、缓冲和碎片预留任何空间
```

### ✅ 企业级改进示例

```java
# 配置值只是示意，最终来自峰值压测，而不是固定比例。
maxmemory 11gb
maxmemory-policy allkeys-lfu
# 同时监控 RSS、COW、客户端缓冲和容器 Working Set。
```

### 🎙️ 2～3 分钟优秀回答

RDB 保存和 AOF 重写通常会 fork 子进程。fork 后父子初始共享物理内存页，依靠 Copy-On-Write 保持快照视图。父进程继续处理写请求时，被修改的页需要复制，因此高写入期间会出现额外 RSS。

延迟来自 fork 页表处理、COW 复制、子进程扫描数据、磁盘 I/O 和资源竞争。数据集越大、写入越高、磁盘越慢、子进程存活越久，风险越大；在容器内还可能触发 OOM Kill。

因此我不会把 maxmemory 直接设到容器上限，而会为 COW、复制/AOF 缓冲、客户端缓冲、碎片和系统空间预留容量，并在真实写流量下执行 BGSAVE/AOF 重写压测，监控 latest_fork_usec、RSS、COW 和后台任务耗时。

### 面试官可能继续追问

- 为什么子进程没有修改数据，父进程写入仍会增加内存？
- THP 和内存碎片为什么可能放大 COW？

> **记忆句**：fork 先共享，父进程一写就复制；maxmemory 必须给 COW 和缓冲留余量。

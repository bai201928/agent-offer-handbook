# Redis 8.8 面试题 Q19

## Q19. 固定窗口、滑动窗口、令牌桶怎样选择

**类型：高频限流题｜难度：中等｜重要性：★★★★☆**

### ① 固定窗口

例如每分钟最多 100 次：

```text
15:00:00～15:00:59 一个计数 Key
```

优点：

- 简单；
- 内存少；
- 易理解。

缺点：窗口边界突刺。

```text
14:59:59 放过 100 次
15:00:00 又放过 100 次
```

短时间可能通过 200 次。

### ② 滑动日志/滑动窗口

使用 ZSet 记录每次请求时间：

```text
删除窗口外记录
统计窗口内数量
加入本次请求
```

优点：更精确。

缺点：

- 每个请求保存成员；
- 热 Key 和内存成本高；
- 操作通常是 O(logN)；
- 需要原子脚本。

### ③ 令牌桶

桶按速率补充令牌，请求消耗令牌。

允许一定突发：

```text
长期平均速率受控
短时间可使用桶内积累
```

适合 API 限流与调用预算。

### ④ 漏桶

请求先进入桶，以固定速度流出，强调平滑处理。

适合保护固定处理能力的下游，但会引入排队和等待。

### ⑤ Redis 8.8 INCREX

适合窗口计数，把增长、边界和过期组合在单命令中。它不能自动替你决定：

- 按租户还是按用户；
- 总额度；
- 突发容量；
- Redis 故障策略；
- 额度分层。

### ⑥ 项目选型

| 场景 | 方案 |
|---|---|
| 登录验证码 | 固定窗口/INCREX |
| 普通 API QPS | 令牌桶 |
| 精确风控统计 | 滑动窗口 |
| 保护 LLM 平稳调用 | 令牌桶＋并发 Semaphore |
| 保护数据库写入 | 入口限流＋舱壁，不只 Redis |

### ⑦ Fail-Open 还是 Fail-Closed

- 推荐、统计等非安全场景，可考虑 Fail-Open；
- 登录、支付、风控、防刷可能 Fail-Closed；
- 不能统一回答，必须按安全和可用性权衡。

### ❌ 容易制造事故的写法

```java
// 每个请求都创建随机 Key，无法形成同一租户窗口。
String key = "rate:" + tenantId + ":" + UUID.randomUUID();
redis.incr(key);
```

### ✅ 企业级改进示例

```java
String key = "rate:{tenant:%s}:%s".formatted(
        tenantId, currentMinuteBucket());
long used = atomicIncrementWithExpiry(key, 60);
if (used > tenantQuota) {
    throw new TooManyRequestsException();
}
```

### 🎙️ 2～3 分钟优秀回答

固定窗口用一个时间段的计数器，简单省内存，但边界可能瞬间放过双倍请求。滑动窗口通常用 ZSet 保存时间戳，更精确但内存和操作成本更高。令牌桶按速率补充令牌，既控制长期平均速率，又允许有限突发，适合大多数 API；漏桶强调固定速度流出，更适合平滑下游。

Redis 8.8 的 INCREX 可以把窗口计数、边界和过期组合成单命令，但算法选择仍取决于业务。NexusAgent 中，租户 API 使用令牌桶，LLM 调用再叠加并发 Semaphore，验证码使用窗口计数。

Redis 故障时是否开放也要分场景：推荐可 Fail-Open，支付和风控可能 Fail-Closed。限流不是只写一个 Key，而是容量、安全和降级策略的组合。

### 面试官可能继续追问

- 令牌桶怎样同时限制 QPS 与并发数？
- 滑动窗口的 ZSet 成员怎样保证唯一？

> **记忆句**：固定窗口简单但有边界；滑动窗口精确但更贵；令牌桶最适合可突发 API。

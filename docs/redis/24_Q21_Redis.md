# Redis 8.8 面试题 Q21

## Q21. 过期删除与内存淘汰有什么区别

**类型：高频基础题＋事故题｜难度：简单偏中等｜重要性：★★★★★**

### ① 先用两个完全不同的问题理解

#### 过期

业务给 Key 设置了 TTL：

```redis
SET session:U1 "..." EX 1800
```

1800 秒后，这份 Session 不应继续有效。

#### 淘汰

Redis 达到 `maxmemory`，新写入需要空间，于是根据策略删除某些 Key。

```text
过期 = 业务生命周期结束
淘汰 = 容量不足，被迫腾空间
```

### ② Key 到期后是否在那一毫秒立刻从内存消失

不一定。

Redis 通常结合：

- 惰性过期；
- 主动过期。

惰性过期：

```text
客户端访问 Key
  ↓
发现已经过期
  ↓
删除并当成不存在
```

主动过期：

```text
Redis 周期性抽样检查有 TTL 的 Key
  ↓
删除已过期项
  ↓
根据命中情况决定是否继续投入清理
```

因此业务上应把到期 Key 视为无效，但物理内存释放可能稍后发生。

### ③ 为什么不扫描全部 Key

如果每毫秒扫描所有 Key，会消耗大量 CPU。Redis 使用抽样和自适应清理，在 CPU 与过期内存之间权衡。

### ④ 淘汰发生在什么时候

新命令需要内存，Redis 判断已超过 `maxmemory`，根据策略：

- 拒绝写；
- 或选择 Key 淘汰。

淘汰不要求 Key 已过期。

### ⑤ 为什么锁和幂等记录不能和普通缓存随意混放

普通结果缓存被淘汰，只是下次回源。

锁或幂等 Key 被淘汰，可能导致：

- 两个 Worker 同时执行；
- 同一支付重复；
- 限流额度重置；
- Checkpoint 丢失。

因此应按正确性分实例、分策略和分容量。

### ⑥ 监控

- expired_keys；
- evicted_keys；
- TTL 分布；
- 内存使用；
- 拒绝写；
- 主动过期时间；
- 业务重建率。

`expired_keys` 上升是生命周期变化；`evicted_keys` 上升通常提示容量或策略问题。

### ❌ 容易制造事故的写法

```java
// 缓存、锁、幂等全部写入同一个 allkeys-lru 实例。
redis.setex("lock:" + runId, 30, owner);
redis.setex("idempotency:" + eventId, 86400, "DONE");
```

### ✅ 企业级改进示例

```java
// 普通可重建缓存使用可淘汰实例。
// 锁、幂等和关键状态进入独立容量池，并采用匹配的策略与事实源兜底。
criticalRedis.set(lockKey, owner, nxPx(30_000));
```

### 🎙️ 2～3 分钟优秀回答

过期和淘汰是两套机制。过期由业务 TTL 决定，表示数据生命周期结束；淘汰由 maxmemory 压力触发，为新写入腾空间，Key 即使没有过期也可能被删除。

Key 到期后不一定在同一毫秒物理删除。Redis 通过访问时的惰性过期和周期性的主动过期清理，避免全量扫描消耗过多 CPU。业务读取时会把已到期 Key 当成不存在。

淘汰策略必须与数据性质匹配。普通缓存被淘汰可以回源，但锁、幂等、限流和 Checkpoint 被淘汰可能改变业务正确性，因此通常与普通缓存隔离。监控上我会区分 expired_keys 和 evicted_keys，前者反映生命周期，后者反映容量压力。

### 面试官可能继续追问

- 为什么 Key 已经过期，used_memory 仍可能暂时不下降？
- 主动过期参数是否应该无条件调高？

> **记忆句**：过期是保质期，淘汰是货架不够；两者触发原因完全不同。

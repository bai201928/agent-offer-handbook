# 第二章：互联网大厂常问独立系统设计

> 本章先回答不依赖项目背景的常问题，再进入项目深挖。

## Q06. 如何设计一个秒杀系统？

**题型**：必问场景系统设计题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

活动开始瞬间 10 万用户请求 10 件商品，目标是不超卖、不重复下单、核心链路可降级且数据库不被击穿。

### 2. 初学者先记住什么

> 关键对象：activity、sku_stock、seckill_qualification、order、payment_deadline；唯一键通常包含 activityId + userId 或 requestId。

### 3. 设计步骤

1. 入口用静态化、CDN、活动资格、验证码/人机识别和用户/设备/商品多维限流减少无效流量。
2. 活动库存提前加载到独立热点存储或库存服务，原子扣减并生成唯一抢购资格。
3. 成功资格写入消息队列削峰，订单消费者依据用户+活动唯一约束幂等创建订单。
4. 数据库保存订单和最终库存事实，异步对账 Redis 预扣、消息和订单。
5. 失败返回明确结果；支付超时释放资格，补偿操作必须带版本和业务 ID。

### 4. 容易制造事故的回答

> 所有请求直接执行库存 UPDATE，然后插入订单并同步调用支付、短信。

### 5. 企业级可落地方案

> 入口过滤 → 原子资格 → MQ 削峰 → 幂等订单 → 延迟关闭 → 对账；Redis 只是高速闸门，订单/库存事实仍要可审计。

### 6. 2～3 分钟面试口述回答

秒杀系统的目标不是让 10 万请求都进入数据库，而是尽早过滤无效流量，并保证只有 10 个有效资格。入口层我会使用 CDN、静态页面、活动资格校验、用户和设备限流以及防机器人。核心库存提前加载到隔离的热点存储或库存服务，通过 Lua 或单线程库存服务原子判断库存、用户是否已抢，再扣减并生成稳定资格 ID。

获得资格的请求进入 MQ 削峰，订单消费者用 activityId 加 userId 或 requestId 的唯一约束幂等创建订单。订单和最终业务状态保存在 MySQL，支付超时后通过延迟消息或时间轮关闭订单并释放资格。整个链路需要对账 Redis 预扣、MQ 消费和订单事实。降级时可以关闭非核心查询、排队页和实时统计，但不能放松库存不超卖和重复下单约束。

### 7. 递进追问

- Redis 扣减成功但 MQ 发送失败怎么办？
- 热点商品 Key 打满单节点如何处理？

## Q07. 10 万顾客抢 10 个库存，如何证明不超卖且最终库存正确？

**题型**：资深并发深挖题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

系统已经有秒杀架构，面试官继续追问：Redis 成功扣了 10 次，但消费者重启、消息重复、用户取消和支付超时同时发生。

### 2. 初学者先记住什么

> 核心不变量不是“Redis 数字永远等于数据库”，而是业务库存守恒和一个 reservation 只结算或释放一次。

### 3. 设计步骤

1. 定义库存状态：可售、预占、已售、释放中，避免只维护一个整数。
2. 使用稳定 reservationId；预占操作必须原子且幂等。
3. 订单创建用唯一约束，消息重复只能返回同一结果。
4. 支付确认以订单状态机条件更新完成，取消和超时释放同一个 reservationId。
5. 周期对账：初始库存 = 可售 + 有效预占 + 已售，并修复孤儿预占。

### 4. 容易制造事故的回答

> 消费失败时直接增加库存；重复消息再次加库存，最终可能多卖。

### 5. 企业级可落地方案

> 库存动作按 reservationId 记录，状态从 RESERVED 只能迁移到 CONFIRMED 或 RELEASED；补偿使用条件更新。

### 6. 2～3 分钟面试口述回答

要证明 10 万人抢 10 件不超卖，我不会只说 Redis 原子减库存，而会定义库存守恒和预占状态。每次成功抢购生成稳定 reservationId，原子地从可售转成预占。订单消费者即使收到重复消息，也通过唯一 reservationId 只创建一个订单。支付成功时预占状态从 RESERVED 条件更新为 CONFIRMED；取消或超时则从 RESERVED 变为 RELEASED，只有状态迁移成功的一方才能归还库存。

这样重复消息、消费者重启和支付回调乱序都不会重复增加或扣减。后台对账验证初始库存等于可售、有效预占和已售之和，并扫描超时孤儿预占。Redis 可以承担高速资格判断，但数据库或库存领域日志要保留可审计事实。真正的正确性证据是唯一键、条件更新和库存不变量，而不是一次压测没有报错。

### 7. 递进追问

- 预占记录量很大怎么清理？
- 数据库与 Redis 对账发现差异谁覆盖谁？

## Q08. 让你设计一个 RPC 框架，应该怎么设计？

**题型**：常问系统设计题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

需要让 Java 服务像调用本地接口一样调用远程服务，并支持注册发现、负载均衡、超时、重试、序列化和可观测性。

### 2. 初学者先记住什么

> 核心对象：serviceKey、methodId、requestId、deadline、codec、status；协议成功不等于业务成功。

### 3. 设计步骤

1. 定义接口代理：动态代理把方法、参数、接口版本转换成 Request。
2. 设计协议：请求 ID、服务/方法、版本、超时、元数据、Payload、错误码和流控字段。
3. 传输层使用连接复用、心跳、编解码、请求响应关联和有界写队列。
4. 注册发现与路由：实例、版本、权重、区域、健康状态；负载均衡与熔断。
5. 治理：绝对 deadline、幂等重试、限流、Tracing、指标、灰度和兼容性。

### 4. 容易制造事故的回答

> 捕获所有异常后自动重试三次；没有 deadline、幂等标记和错误分类。

### 5. 企业级可落地方案

> 只对明确可重试错误重试，沿调用链传播剩余时间；写操作必须由业务声明幂等键。

### 6. 2～3 分钟面试口述回答

RPC 框架我会按代理、协议、传输、发现路由和治理五层设计。客户端动态代理把接口调用转换成包含 service、method、version、requestId、deadline 和元数据的请求；协议层定义帧长度、序列化、压缩、状态码和错误分类；传输层负责连接复用、心跳、编解码、请求响应关联和有界队列。

注册中心保存服务实例、版本、权重和区域，客户端通过负载均衡选实例，并结合健康检查和熔断。治理重点不是“调用通了”，而是 deadline 贯穿全链、重试只有一个所有者、写操作具有幂等键、限流和舱壁防止级联故障。还要提供 Trace、延迟直方图、错误码、连接池和在途请求指标，以及协议和接口版本兼容。首版可以只支持请求响应，流式、多路复用和自适应并发后续演进。

### 7. 递进追问

- 如何避免请求 ID 冲突？
- 服务端已经执行但响应丢失怎么办？

## Q09. 让你设计一个短链系统，怎么设计？

**题型**：常问系统设计题  
**实际难度**：中等偏上  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

用户提交长 URL，系统返回短码；访问短链要求低延迟、高可用、支持过期、风控和点击统计。

### 2. 初学者先记住什么

> 表至少包含 shortCode、longUrl、tenantId、status、expireAt、createdAt；短码必须受域名/租户作用域约束。

### 3. 设计步骤

1. 写链路：校验 URL 与租户权限，生成短码，唯一约束写入映射表。
2. 读链路：域名+短码查询缓存，未命中查数据库，返回 301/302。
3. 短码生成可用自增/雪花 ID 转 Base62、随机码加唯一冲突重试或号段。
4. 热点映射多级缓存；不存在短码做短 TTL 空值和防枚举限流。
5. 点击统计异步写消息流，主跳转链不等待统计。

### 4. 容易制造事故的回答

> 使用长 URL 的普通 hash 截断为 6 位，不检测碰撞；每次跳转同步更新点击次数。

### 5. 企业级可落地方案

> 数据库唯一约束保证短码唯一；跳转和统计解耦，失效/恶意链接由状态和风控裁决。

### 6. 2～3 分钟面试口述回答

短链系统分创建和跳转两条链。创建时校验长 URL、租户和安全策略，生成短码并依赖数据库唯一约束落库。短码可以使用全局 ID 转 Base62，也可以随机生成后冲突重试；不能只截断哈希而不处理碰撞。跳转时先查本地或 Redis 缓存，再查数据库，校验状态和过期时间后返回 301 或 302。

读流量通常远高于写流量，所以热点短链要缓存和限流，恶意枚举要做频率控制，不存在短码可短期缓存空值。点击统计、地域和设备分析应异步写 MQ，不阻塞跳转。数据库需要按域名或租户规划分片，缓存包含版本/状态，禁用短链后必须让失效尽快传播。最后用命中率、跳转 P99、创建冲突率、无效访问和统计积压验证。

### 7. 递进追问

- 301 和 302 如何选择？
- 同一个长 URL 是否必须生成同一个短码？

## Q10. 如何设计一个点赞系统？

**题型**：常问系统设计题  
**实际难度**：中等偏上  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

帖子点赞读多写多，需要支持用户是否点赞、总点赞数、取消点赞、消息流展示和热门内容。

### 2. 初学者先记住什么

> 不能只保存 count；没有用户-目标明细就无法可靠处理重复点赞、取消和审计。

### 3. 设计步骤

1. 事实模型使用 userId+targetType+targetId 唯一约束，状态可用存在记录或 active 标记。
2. 写接口带 requestId 幂等，点赞/取消通过条件写防止重复计数。
3. 计数可异步聚合到 Redis/计数表，最终以点赞明细或事件对账。
4. 查询分为是否点赞、点赞数、点赞用户列表，分别设计索引与缓存。
5. 热点内容分片计数、批量合并；消息通知异步且去重。

### 4. 容易制造事故的回答

> 先查询是否点赞，再插入并增加 count；并发请求可重复加一。

### 5. 企业级可落地方案

> 唯一键负责一次有效点赞，状态迁移成功后才产生计数事件；计数是可重建派生值。

### 6. 2～3 分钟面试口述回答

点赞系统至少包含点赞关系和点赞计数两个模型。关系表以 userId、targetType、targetId 建唯一约束，决定某用户是否点赞；计数是从关系或事件派生的热点数据。写入时不能先查再写，而应通过唯一键或条件更新保证一次有效状态迁移，再发送计数事件。取消点赞同样只有从 active 到 inactive 成功时才能减计数。

查询侧，是否点赞适合按用户和目标快速判断，总数可在 Redis 或计数表缓存，点赞用户列表需要按目标和时间分页。超级热点可以把计数拆成多个分片再聚合，避免单 Key 写热点。通知、动态流和排行榜异步处理，并通过 eventId 去重。系统要监控关系事实与计数差异，定期对账，保证重复请求、消息重放和缓存丢失不会造成永久错数。

### 7. 递进追问

- 计数允许近似吗？
- 热门帖子单 Key 写热点怎样拆？

## Q11. 让你设计一个分布式 ID 发号器，怎么设计？

**题型**：常问系统设计题  
**实际难度**：中等偏上  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

多个机房和服务需要生成全局唯一 ID，还希望大致有序、低延迟并能从 ID 识别时间或分片。

### 2. 初学者先记住什么

> 业务幂等键和数据库主键不是同一个概念；ID 唯一不能自动防止同一业务重复提交。

### 3. 设计步骤

1. 先确认需求：全局唯一、趋势递增、是否严格递增、吞吐、位数、跨区域和时钟容忍。
2. 数据库自增简单但中心瓶颈；号段模式批量申请区间，降低数据库访问。
3. Snowflake 类方案按时间戳+区域/机器+序列生成，需治理时钟回拨和机器 ID。
4. UUID 简单但索引局部性差；可使用时间有序 UUID/ULID 类标识。
5. 服务需持久化节点租约、监控冲突/回拨，并提供降级与容量计划。

### 4. 容易制造事故的回答

> 用当前毫秒时间戳作为 ID；同毫秒并发和多节点会碰撞。

### 5. 企业级可落地方案

> 明确位分配和寿命，机器 ID 通过租约管理；时钟回拨时停发、等待或切换逻辑时钟。

### 6. 2～3 分钟面试口述回答

分布式 ID 先看需求，不一定都用 Snowflake。若需要严格全局递增，通常要中心协调，吞吐和可用性成本较高；大多数业务只要求全局唯一和趋势递增。数据库自增实现简单但中心压力大，号段模式让服务一次申请一段 ID，吞吐和可用性更好。Snowflake 使用时间戳、节点 ID 和序列，适合高吞吐，但必须解决机器 ID 分配、时钟回拨、位数寿命和跨机房问题。

UUID 无中心但较长且随机写索引成本高，可选时间有序标识。无论哪种方案，都要监控重复、号段耗尽、时钟偏移和节点租约，并设计降级。还要强调分布式 ID 只保证技术唯一，业务重复仍需 orderNo、requestId 等幂等键和唯一约束。

### 7. 递进追问

- Snowflake 时钟回拨如何处理？
- 为什么严格递增比趋势递增昂贵？

## Q12. 订单半小时未支付自动取消，应该怎么实现？

**题型**：常问场景题  
**实际难度**：中等偏上  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

订单创建后 30 分钟未支付需要关闭并释放库存；支付回调可能与取消任务同时到达。

### 2. 初学者先记住什么

> 延迟消息不是事实源；消息可能丢、重复、提前或迟到，最终裁决来自订单状态和 expireAt。

### 3. 设计步骤

1. 订单保存 expireAt 和状态，创建时写延迟消息或进入时间轮/延迟队列。
2. 到期任务只作为触发，执行时重新读取订单事实。
3. 用条件更新 PENDING → CANCELED；只有成功者释放库存。
4. 支付回调同样条件更新 PENDING → PAID，数据库状态机决定竞态结果。
5. 提供定时扫描兜底，扫描过期未终态订单并分片处理。

### 4. 容易制造事故的回答

> 收到延迟消息就无条件取消订单并加回库存。

### 5. 企业级可落地方案

> 延迟消息携带 orderId/eventId；消费者重读订单，检查 deadline 和当前状态，条件更新成功后发释放事件。

### 6. 2～3 分钟面试口述回答

半小时取消我会使用“延迟触发加数据库状态机加扫描兜底”。订单创建时保存 expireAt，并发送延迟消息或写入时间轮。消息到期只是提醒系统检查，不能直接当成订单一定未支付。消费者读取订单，只有状态仍为 PENDING 且已经到期时，条件更新为 CANCELED；只有更新成功的一方才能释放库存。

支付回调也只能把 PENDING 更新为 PAID，因此支付和取消并发时由数据库条件更新决定唯一结果。消息可能重复、迟到或丢失，所以消费者使用稳定 eventId 幂等，同时周期扫描过期未终态订单兜底。小规模可用数据库扫描，中大规模用 RocketMQ 延迟消息、时间轮或分桶 ZSet，但无论使用什么调度组件，最终正确性都依赖订单状态机。

### 7. 递进追问

- 延迟消息早到怎么办？
- 海量订单扫描怎样避免全表扫描？

## Q13. 系统 QPS 突然提升 10 倍，你会怎样设计和处置？

**题型**：高频场景系统设计题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

活动流量从 2,000 QPS 升到 20,000 QPS，模型、数据库和缓存扩容速度不同，重试开始放大。

### 2. 初学者先记住什么

> 十倍 QPS 不等于每层都十倍扩容；缓存命中、请求复杂度、写比例和外部调用倍数决定真实负载。

### 3. 设计步骤

1. 先区分真实增长、攻击和重试放大；保护入口与事实库。
2. 立即启用限流、排队、降级、缓存、只读模式和非核心功能关闭。
3. 按链路找首个饱和点：连接池、队列年龄、Redis 热点、DB 锁/I/O、MQ Lag、外部配额。
4. 水平扩无状态服务，垂直/分片扩有状态组件；扩容前确认下游能承接。
5. 长期做容量模型、热点拆分、异步化、自动扩缩容护栏和活动预案。

### 4. 容易制造事故的回答

> 把所有 Pod 扩 10 倍并把超时和连接池都调大。

### 5. 企业级可落地方案

> 先限流/降级止血，按首个饱和点扩容；重试预算和 deadline 防止扩容把压力继续传给下游。

### 6. 2～3 分钟面试口述回答

QPS 突然十倍时，我先判断是业务增长、攻击还是重试风暴，并立即保护入口和事实库。短期措施包括按用户和租户限流、关闭非核心功能、缓存热点、只读降级、异步排队和控制消费者并发。排查时看端到端 Trace 和各层原因指标，找第一个饱和点，而不是只看 CPU。

无状态服务可以水平扩容，但数据库、Redis 热点、消息分区和外部模型配额未必能同步扩。盲目增加 Pod、连接池和超时可能让下游更快崩溃。因此扩容要配合舱壁、总 deadline、单层重试、队列年龄和拒绝策略。长期通过真实流量回放、突发压测、热点拆分、读写分离、分片和活动容量预案，使系统在目标 SLO 下拥有经过验证的余量。

### 7. 递进追问

- CPU 只有 40% 为什么仍不能继续接流量？
- 限流应该放在哪几层？

## Q14. 大流量网站单 Redis 无法承压，应该如何演进？

**题型**：常问系统设计题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

单 Redis CPU、网络或内存达到瓶颈，并且存在一个超级热点 Key；团队想直接上 Cluster。

### 2. 初学者先记住什么

> Cluster 只能按 Key 分片；单个超热 Key 仍落在一个主节点，不能自动横向拆开。

### 3. 设计步骤

1. 先确认瓶颈是容量、CPU、网络、大 Key、热 Key、慢命令还是客户端队头阻塞。
2. 读热点先用本地缓存、请求合并、热点副本和预热；写热点需拆业务对象或分片计数。
3. 容量/吞吐不足再引入 Redis Cluster，设计 Key 和 Hash Tag，避免 Hot Slot。
4. 可接受陈旧读可使用副本，但复制延迟和故障窗口必须明确。
5. 缓存与协调状态分池，设置大小/TTL/淘汰边界并提供事实源回建。

### 4. 容易制造事故的回答

> 所有 Key 使用 `{tenantId}` Hash Tag，把超级租户全部固定在一个 Slot。

### 5. 企业级可落地方案

> 只把最小原子单元同槽；热计数分桶，读聚合；协调状态与普通缓存独立。

### 6. 2～3 分钟面试口述回答

单 Redis 无法承压时，我先定位瓶颈。可能是内存不足，也可能是网络、大 Key、热 Key、O(N) 命令或客户端大回复。读热点优先通过 JVM 本地缓存、请求合并和热点副本缓解；写热点要拆业务对象或把计数分桶，因为 Redis Cluster 只能按 Key 分片，单个热 Key 仍然压在一个节点。

整体容量或吞吐不足时再引入 Cluster，Key 设计要避免过粗 Hash Tag 和 Hot Slot。读副本只适合允许陈旧的数据，不能解决写热点。普通可重建缓存可以使用淘汰策略，锁、幂等和租约等协调状态应隔离容量并避免误淘汰。扩容还要校验客户端拓扑刷新、迁槽、MOVED/ASK、故障转移和回源保护。

### 7. 递进追问

- 单个热 Key 如何拆？
- Redis Cluster 迁槽期间客户端如何处理？

## Q15. 如何设计一个可重入的分布式锁，用什么结构？

**题型**：常问并发设计题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

同一业务执行链会嵌套调用同一把锁，需要可重入；进程崩溃、锁过期和旧持有者继续写都可能发生。

### 2. 初学者先记住什么

> ownerToken 必须代表一次执行身份，不能只用线程 ID；跨进程/重启后线程 ID 不唯一。

### 3. 设计步骤

1. 锁 Key 映射一个 Hash：field=ownerToken，value=reentryCount，并设置租约 TTL。
2. 加锁脚本：Key 不存在则创建；同 owner 则计数+1；其他 owner 返回失败。
3. 解锁脚本：验证 owner，计数-1；归零才删除；非 owner 不得释放。
4. 续租只允许当前 owner，并限制最大持有时间和失联行为。
5. 真正写共享事实时使用 fencing token 或数据库 version 拒绝过期旧持有者。

### 4. 容易制造事故的回答

> SETNX 锁后，解锁时直接 DEL；锁过期后旧线程仍可能删除新持有者的锁。

### 5. 企业级可落地方案

> Lua 原子判断 owner 和计数；锁只提供互斥提示，外部资源用 fencing/version 保护。

### 6. 2～3 分钟面试口述回答

可重入分布式锁可以使用 Redis Hash 保存 ownerToken 到重入次数，并给整个 Key 设置租约。加锁通过 Lua 原子完成：Key 不存在时写入 owner 和计数 1；如果 owner 相同则计数加一并续租；其他 owner 获取失败。解锁时同样验证 owner，计数减一，只有归零才删除，避免误删别人的锁。

owner 不能只用线程 ID，而应包含实例、进程和一次执行 ID。还要处理崩溃和租约过期，续租只能由当前 owner 执行，并设置业务最大时长。更重要的是，Redis 锁不能阻止租约过期后的旧线程继续操作数据库或外部系统，所以关键写入要携带单调 fencing token 或版本号，由资源端拒绝旧写。可重入、互斥、Fencing 和幂等分别解决不同问题。

### 7. 递进追问

- Redisson 看门狗解决了什么、没解决什么？
- 锁服务故障时业务应失败开放还是失败关闭？

## Q16. 什么是微服务架构，它解决什么，又带来什么？

**题型**：常问架构题  
**实际难度**：中等  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

团队把 Controller、Redis、MQ、数据库访问分别拆成服务，服务很多但领域边界和数据所有权更混乱。

### 2. 初学者先记住什么

> 服务数量不是微服务成熟度；共享一张数据库并跨服务随意写表，通常仍是分布式单体。

### 3. 设计步骤

1. 微服务围绕业务能力和数据所有权独立演进，而不是按技术层拆服务。
2. 服务应有清晰 API/事件契约、独立发布和可观测边界。
3. 收益：独立扩缩容、故障隔离、团队自治和技术演进。
4. 成本：网络失败、分布式一致性、测试部署、观测、安全和运维复杂度。
5. 小团队或早期业务优先模块化单体，边界成熟且收益明确再拆。

### 4. 容易制造事故的回答

> 把 UserController、UserService、UserDAO 拆成三个服务。

### 5. 企业级可落地方案

> 按用户身份、订单、库存、支付等业务能力划界，每个事实表只有一个服务拥有写权。

### 6. 2～3 分钟面试口述回答

微服务不是把代码切成很多进程，而是围绕业务能力和数据所有权形成可以独立演进、发布和扩缩容的服务边界。它适合团队和业务规模已经出现独立节奏、独立容量或故障隔离需求的场景。收益包括局部扩容、技术自治和缩小发布影响面。

代价是每次本地调用变成不可靠网络调用，跨服务事务、重复消息、版本兼容、观测、安全和运维都更复杂。共享数据库并互相改表会形成分布式单体。因此我通常从模块化单体开始，用清晰模块、接口和数据所有权验证边界；当某模块有独立扩容、合规隔离、团队自治或发布节奏需求时，再通过 API 和事件拆出微服务。

### 7. 递进追问

- 微服务是否必须每服务一个数据库？
- 服务粒度怎么判断过大或过小？

## Q17. 一个现有单体项目，怎样逐步拆成微服务？

**题型**：常问项目场景题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 1. 为什么会问这道题

单体包含用户、订单、库存、支付、通知和 Agent 功能，发布慢、热点不同，但代码和表强耦合。

### 2. 初学者先记住什么

> 拆分顺序通常不是按代码行数，而是按业务耦合、数据归属、独立容量和失败隔离收益。

### 3. 设计步骤

1. 先建立模块边界、依赖图、数据所有权和契约测试，不直接物理拆分。
2. 选择业务价值高且边界清楚的切口，例如通知、文件处理或独立查询。
3. 使用 Strangler 模式：新流量逐步路由到新服务，保留回退。
4. 拆数据时由原所有者提供 API/事件，使用 Outbox 同步新服务投影，禁止双写。
5. 逐步迁移、观测、对账、灰度和回滚；最后移除旧路径。

### 4. 容易制造事故的回答

> 一次性把代码复制到多个仓库，多个服务继续直连同一数据库并修改同一表。

### 5. 企业级可落地方案

> 先模块化、再契约化、后进程化和数据化；每一步都能回滚和对账。

### 6. 2～3 分钟面试口述回答

拆单体我不会先建几十个仓库，而会先把单体内部模块化，画依赖和数据所有权。选择一个边界清晰、失败风险较低且有独立扩容价值的能力作为切口，通过 Strangler 模式逐步把流量路由到新服务。原单体暂时仍是事实源，新服务通过 API 或 Outbox 事件构建自己的数据视图，避免数据库和消息双写。

迁移期间要有契约测试、双读比对、流量灰度、监控和一键回退。等新服务稳定并成为唯一写入者后，再迁移数据所有权并删除旧路径。订单、库存、支付这类核心域拆分要最后处理，因为跨域一致性和补偿复杂。拆分成功的标准不是服务数增加，而是边界清晰、独立发布扩容、故障不扩散且业务状态可对账。

### 7. 递进追问

- 第一个服务应该选什么？
- 共享数据库过渡期怎样限制风险？

# 第三章：幂等、跨组件可靠性与分布式一致性

## Q18. 如何设计一个高并发接口的防重、幂等和重复请求处理？

**题型**：高频场景题  
**实际难度**：中等偏上  
**学习层级**：进阶加分题

### 为什么会问

客户端超时、网关重试和用户重复点击，可能让创建订单、提交任务等接口被调用多次。

### 核心设计

1. 首次请求生成稳定 `idempotencyKey`，重试不能换 Key。
2. 数据库用 `tenant_id + idempotency_key` 唯一约束原子创建处理记录。
3. 保存 `PROCESSING / SUCCEEDED / UNKNOWN / FAILED_RETRYABLE` 和结果摘要。
4. 重复请求返回同一结果或“处理中”，不能再次执行。
5. 外部副作用使用稳定 `operationId`，未知结果通过查询和对账裁决。

### 容易制造事故的设计

> 只使用一个 5 秒过期的 Redis `SETNX` 防重。Key 过期、淘汰或故障切换后，重复业务仍会进入事实库。

### 2～3 分钟面试口述回答

高并发接口防重的核心是稳定业务身份和数据库唯一约束。客户端第一次请求生成 idempotencyKey，所有超时重试必须沿用；服务端以租户和业务键建立唯一约束，原子写入处理记录，并保存处理中、成功或未知等状态和结果摘要。

重复请求到来时，若已成功就返回同一结果；仍处理中就返回处理中或等待原请求。Redis SETNX 可以作为快速拦截，但不能成为最终正确性来源。涉及支付或外部工具时，还要使用稳定 operationId；调用超时不能换 ID 盲重试，而要查询远端、进入 UNKNOWN 或人工对账。幂等的标准不是每次返回相同文本，而是重复执行只产生一个等价业务效果。

### 递进追问

- 幂等记录保存多久？
- 失败后是否允许相同 Key 再次执行？

## Q19. 跨 MySQL、Redis、MQ 和搜索/向量库，为什么必须先指定事实源？

**题型**：高薪可靠性题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 初学者先记住

> 同一个系统可以有多个领域事实源，但同一项状态只能有一个最终裁决者。

### 设计步骤

1. 分别定义业务状态、权限、知识发布、缓存、索引和消息投递的所有者。
2. MySQL/领域服务保存不可随意丢失的业务事实。
3. Redis、搜索和 Milvus 保存带来源版本的派生状态。
4. MQ 负责传播和调度，不自动成为所有业务的最终事实。
5. 使用 `sourceVersion`、重建、校验和与 Reconciler 让派生状态收敛。

### 2～3 分钟面试口述回答

跨组件设计第一件事是逐项指定事实源。订单、权限和知识发布版本等业务事实通常由领域服务和 MySQL 事务裁决；Redis 是热点缓存，搜索或 Milvus 是可重建索引，MQ 是事件传播和任务触发。它们都可能暂时陈旧、重复或丢失，因此不能与业务表同时拥有最终写权。

事实变化通过带稳定 eventId 和 sourceVersion 的事件传播，消费者幂等更新派生视图，旧版本不得覆盖新版本。读取时若权限或索引版本落后，应拒绝、回源或降级，而不是返回可能越权的数据。Reconciler 从事实源扫描和重建缓存、索引。这样组件发生分裂时，系统仍然知道信谁、怎样恢复以及怎样证明恢复完整。

### 递进追问

- 事件日志什么时候可以成为事实源？
- 如何证明派生索引重建完整？

## Q20. 一次写请求有哪些不同 ACK，为什么 HTTP 200 不等于业务完成？

**题型**：资深可靠性题  
**实际难度**：困难  
**学习层级**：进阶加分题

### 不同确认层级

```text
网关收到请求
→ 应用进入内存队列
→ 数据库本地事务提交
→ 副本确认
→ MQ Broker 持久化
→ 消费者业务事务提交
→ 外部副作用真正完成
```

### 2～3 分钟面试口述回答

HTTP 200、数据库提交、MQ 发送成功和消费者 ACK 分别代表不同层级。网关收到请求只表示接收；写入应用内存队列不是耐久；数据库 COMMIT 表示本地业务事实已提交；Broker ACK 表示消息达到其约定的存储等级；消费者 ACK 也要区分收到、处理和业务事务提交。外部 HTTP 200 还要看契约是“已受理”还是“副作用已完成”。

因此 API 必须声明承诺边界。长任务可以返回 202 和 runId，表示已经耐久受理；只有所有业务后置条件和副作用证据齐全，才标记 COMPLETED。每个阶段持久化状态和稳定 ID，超时后重读事实，不凭本地异常猜远端失败。可靠系统的核心就是不把局部 ACK 外推成端到端成功。

### 递进追问

- 生产者超时但 Broker 可能已写入怎么办？
- 消费者在什么时点 ACK 最安全？

## Q21. Transactional Outbox 与 Inbox 怎样关闭数据库和 MQ 的双写窗口？

**题型**：高频可靠性题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 正常链

```text
业务表 + outbox_event 同一本地事务提交
→ Relay/CDC 至少一次发布
→ 消费者用 eventId 写 Inbox
→ Inbox 与消费者业务更新同事务提交
```

### 关键边界

- Outbox 解决业务提交与事件创建的原子性。
- Outbox 不保证只发送一次。
- Inbox 让重复投递只产生一次有效业务处理。
- 两者都不能自动回滚外部支付或 MCP 工具。

### 2～3 分钟面试口述回答

Transactional Outbox 把业务状态和待发布事件写在同一个数据库事务中，因此只会两者都提交或都不提交，不再存在订单已成功但事件完全丢失的随机双写窗口。独立 Relay 或 CDC 至少一次发布 Outbox，所以消息可能重复。

消费者使用 Inbox，以业务 eventId 建唯一约束，在同一本地事务中记录事件已处理并更新自己的业务状态。重复消息只返回已有处理结果。Outbox/Inbox 没有提供全局 exactly-once，也没有自动处理外部副作用或无限积压，因此仍需重试上限、死信、事件版本、Lag 告警和 Reconciler。它们的价值是把不可恢复窗口变成可扫描、可重放和可对账的持久状态。

- Outbox 表会不会成为写入瓶颈？
- CDC 和轮询 Relay 如何选择？

## Q22. 重复、乱序、迟到回调、旧 Worker 和多层重试怎样统一治理？

**题型**：资深可靠性题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 四类机制

| 问题 | 机制 |
|---|---|
| 重复 | 稳定 eventId/operationId + 唯一约束 |
| 乱序/迟到 | sequence、version、合法状态迁移 |
| 旧 Worker | generation/fencing，资源端拒绝旧写 |
| 重试风暴 | 绝对 deadline、单一重试所有者、预算和退避 |

### 2～3 分钟面试口述回答

我会用四类机制统一治理。第一是稳定身份，eventId 和 operationId 在所有重试中保持不变，配合唯一约束实现幂等。第二是单调 version 或 sequence，迟到事件只有版本更新且状态迁移合法时才能生效。第三是 generation 或 fencing，让旧 Worker 即使恢复也无法覆盖新接管者。第四是总 deadline 和重试预算，只有一个层级拥有业务重试，使用退避和抖动，避免网关、SDK、服务和 MQ 层层放大。

对于支付或 MCP 工具，超时代表结果未知，不能直接标记失败并换 ID 重试，而要持久化 UNKNOWN，使用相同 operationId 查询对端、对账或转人工。幂等解决重复，版本解决新旧，Fencing 解决旧执行者，deadline 和预算解决流量放大。

## Q23. Cache Aside 在并发更新、删除和权限撤销下有哪些陈旧窗口？

**题型**：高频可靠性题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 经典旧回填竞态

```text
A 缓存 Miss，读到数据库 v7
B 更新数据库为 v8，并删除缓存
A 较晚把 v7 回填缓存
```

### 治理

- 版本化 Key 或 Value 携带 version。
- 维护 activeVersion/最低有效版本，拒绝旧回填。
- 数据库提交后的失效通过 Outbox/CDC 重试。
- 权限撤销时，Redis/Milvus 版本落后应拒绝或回源。
- TTL 只是最终兜底，不是并发正确性的证明。

### 2～3 分钟面试口述回答

Cache Aside 的标准流程是缓存 Miss 后查事实源并回填，更新数据库后删除缓存。但并发下仍有旧回填窗口：A 已经读到旧值，B 更新数据库并删除缓存，A 最后又把旧值写回。删除失败、读副本延迟和本地多级缓存还会扩大窗口。

解决方法是让缓存身份带业务版本，或 Value 携带 version 并做条件写；知识和权限可维护 activeVersion，让旧请求只能写旧版本命名空间。事务提交后的失效通过 Outbox 或 CDC 重试，TTL 只是最终兜底。权限撤销属于高风险，如果 Redis 或 Milvus 的权限版本落后，宁可拒绝或回源，也不能返回可能越权的数据。

### 递进追问

- 延迟双删为什么不能单独解决问题？
- 本地缓存如何可靠失效？

## Q24. 高可用、副本、备份和灾备为什么不能互相替代？

**题型**：高薪可靠性题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 四者边界

| 能力 | 主要解决的问题 |
|---|---|
| 高可用 | 局部故障下快速继续服务 |
| 副本 | 冗余和读扩展，可能存在复制延迟 |
| 备份/PITR | 恢复历史数据和误操作 |
| 灾备 | 区域级切换、恢复和业务完整性 |

### 2～3 分钟面试口述回答

高可用、副本、备份和灾备解决的故障范围不同。副本能在节点故障时接管并扩展读，但异步复制可能丢最近写，而且误删和逻辑错误会快速传播。备份用于恢复历史时间点，必须验证备份可读、恢复耗时和保留周期。灾备面对机房或区域故障，除了数据库，还要恢复身份、消息、缓存、索引、密钥、路由和外部副作用。

RPO 表示最多能丢多少数据，RTO 表示多久恢复业务能力，应由业务分级反推复制、备份和降级。真正证据是定期从备份恢复、重放事件、重建派生状态、切流和回切，并通过业务不变量对账。Pod 变绿或副本在线都不等于业务恢复完成。

- PITR 恢复点怎样与 MQ 对齐？
- 自动故障转移为什么仍可能丢已返回成功的写？

## Q25. 如何为 MySQL、Redis、MQ、模型和外部工具建立降级矩阵？

**题型**：项目可靠性题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 设计方法

1. 对每个依赖列出超时、拒绝、陈旧、部分成功和完全不可用。
2. 对业务动作区分只读、可补偿写、不可逆副作用。
3. 每个格子选择失败关闭、失败开放、旧值、排队、转人工或拒绝。
4. 所有降级记录真实状态和质量等级，不能把 UNKNOWN 伪装成 SUCCESS。
5. 用故障注入验证降级后不越权、不超卖、不重复副作用。

### 2～3 分钟面试口述回答

降级矩阵要同时看依赖类型和业务风险。我会为 MySQL、Redis、MQ、模型、Milvus 和外部工具分别列出超时、拒绝、陈旧、部分成功和完全不可用，再按照只读、可补偿写和不可逆副作用选择策略。Redis 失败不能无限回源，要有数据库舱壁；MQ 不可用时事实和 Outbox 可先提交；模型失败可切备用，但必须记录版本和质量降级；工具超时要保持 UNKNOWN，不能盲重试。

权限、资金、库存和高风险工具通常失败关闭；非核心推荐和统计可以延迟。每种降级都要记录原因、版本、影响范围和恢复后的对账动作，并通过故障注入证明降级没有突破业务不变量。

### 递进追问

- 模型切换为什么可能改变业务语义？
- Redis 故障时如何保护 MySQL？

## Q26. 分布式事务应该怎样选择：本地事务、Outbox、Saga、TCC 还是强协调？

**题型**：资深架构题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 选择顺序

```text
能收敛到一个领域和数据库 → 本地事务
异步传播/派生视图 → Outbox + Inbox
长流程且可补偿 → Saga
可提供 Try/Confirm/Cancel → TCC
极少数强一致且参与方支持 → 强协调
```

### 2～3 分钟面试口述回答

分布式事务选择从业务不变量和补偿能力开始。能放在同一服务和数据库的强约束优先本地事务，这是最简单可靠的。跨服务传播以及缓存、搜索等派生状态优先 Outbox/Inbox，接受明确的最终一致窗口。长流程如果每一步都有可验证的业务补偿，可以使用 Saga；补偿不是数据库回滚，而是释放库存、退款等新的业务动作。

TCC 适合参与方能够提供 Try、Confirm、Cancel 并愿意长期维护资源预留的场景。强协调会增加延迟、可用性和运维复杂度，只用于极少数无法接受中间态的业务。外部支付和工具调用不能被本地事务自动回滚，因此需要稳定 operationId、UNKNOWN 和对账。方案不是越强越好，而是用最低复杂度满足业务不变量。

### 递进追问

- Saga 补偿失败怎么办？
- TCC 的空回滚和悬挂是什么？

## Q27. 一致性、可用性和网络分区应怎样表达取舍？

**题型**：资深架构题  
**实际难度**：困难  
**学习层级**：进阶加分题

### 2～3 分钟面试口述回答

我不会只说系统选择 CP 或 AP，而会落到具体数据和操作。网络分区时，如果库存、支付或权限不能接受双写冲突，就需要单写区域、共识或租约加 epoch，另一区域拒绝写或进入只读降级。对于点赞计数、草稿和统计等可合并数据，可以允许多写，再按业务规则、版本向量或 CRDT 收敛。

分区恢复后最危险的是旧主或旧区域继续写，所以切换和回切都需要 generation/fencing，所有写入携带新世代，资源端拒绝旧世代。CAP 不是给整个系统贴一个永久标签，而是说明分区发生时每类数据愿意牺牲什么、如何向用户展示，以及恢复后怎样对账。

### 递进追问

- 怎样保证读己之写？
- 跨区域单写的延迟如何治理？

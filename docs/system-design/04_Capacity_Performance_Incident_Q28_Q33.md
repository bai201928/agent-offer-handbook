# 第四章：容量、压测、稳定性与事故治理

## Q28. 容量规划为什么要按真实工作单位建模，Little 定律如何使用？

**题型**：高频容量题  
**实际难度**：中等偏上  
**学习层级**：70% 必会题

### 为什么会问

普通系统只统计 API QPS，Agent 平台只统计 Run 数，却忽略一个请求可能包含多次数据库、缓存、模型、检索和工具调用。

### 容量单位

```text
普通网站：请求、读、写、对象字节、连接、消息
Agent/RAG：Run、Step、Token、检索、Tool、Checkpoint、人工审批
```

### 设计步骤

1. 按短/长、读/写、在线/批量、普通/热点租户划分工作负载。
2. 统计每类请求的下游调用倍数和服务时间分布。
3. 在近似稳定窗口使用 `L ≈ λW` 估算平均在途量。
4. 同时观察 P95/P99、队列年龄和业务 deadline。
5. 用阶梯压测找到各依赖的首个饱和点并持续校准。

### 2～3 分钟面试口述回答

容量规划必须从真实工作单位开始。普通网站至少区分读、写和大对象；Agent 平台还要统计每个 Run 的 Step 数、模型 Token、检索次数、工具调用、消息和数据库事务。先按任务类型获得到达率和服务时间分布，再用 Little 定律在近似稳定窗口估算平均在途量，但不能忽略 P95/P99 和突发。

随后把 Run 到达率乘以每 Run 的下游调用倍数，得到模型、Milvus、Redis、MySQL 和 MQ 的需求率，通过阶梯压测找到各自首个饱和点。若队列年龄持续上升，系统已经不稳定，即使 CPU 尚低。最终容量还要考虑扩容时间、单节点故障和热点租户，并由生产基线持续校准。

- MQ 恢复后的追赶时间怎样估算？

## Q29. 如何设计真实压测，为什么平均延迟和 Closed-loop 会低估事故？

**题型**：资深性能题  
**实际难度**：困难  
**学习层级**：进阶加分题

### 真实压测必须包含

- 生产读写比例、对象大小和缓存冷热；
- 普通与热点租户；
- 短任务与长尾任务；
- Open-loop 固定到达率；
- 阶梯、突发、长稳态和依赖抖动；
- 节点故障、恢复和积压追赶；
- 业务正确性校验。

### 2～3 分钟面试口述回答

真实压测要复现生产工作负载，而不是循环请求一个小接口。需要包含读写比例、对象大小、缓存冷热、热点租户、长短任务和下游调用分布。Open-loop 按计划到达率发请求，更接近外部用户；Closed-loop 等前一个响应后再发，服务变慢时会自动减小压力，容易低估排队和协调遗漏。

指标不能只看平均值，要看 P95、P99、P99.9、超时、拒绝、队列年龄和业务成功率。测试应包含阶梯升压寻找弯点、突发、长时间稳态、依赖限流、节点故障以及恢复后的积压追赶。压测通过不只意味着吞吐达标，还要证明没有超卖、重复副作用和跨租户泄露。

## Q30. 背压、限流、有界队列、Bulkhead 和 Circuit Breaker 应怎样组合？

**题型**：高频稳定性题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 各机制职责

| 机制 | 解决的问题 |
|---|---|
| Rate Limiter | 控制进入系统的速率 |
| Admission Control | 开始昂贵工作前判断是否有容量 |
| 有界队列 | 限制内存和等待时间 |
| Bulkhead | 隔离依赖、租户和任务并发预算 |
| Circuit Breaker | 依赖持续失败时快速失败 |
| Backpressure | 让上游主动减速或停止生产 |

### 2～3 分钟面试口述回答

这些机制解决不同问题。限流控制进入系统的速率；准入控制在开始昂贵工作前检查容量、队列年龄和剩余 deadline；有界队列限制等待和内存，满时必须拒绝或降级；Bulkhead 把模型、数据库、工具和不同租户的并发隔离，防止一个依赖拖垮全部请求；Circuit Breaker 在持续失败时快速失败，避免继续消耗资源。

背压意味着让上游感知容量并减少生产，不能只把队列调大。重试必须由一个层级拥有，使用总 deadline、指数退避、抖动和预算。恢复时使用半开探测和慢启动逐步放流。组合目标是在过载时有序拒绝并保护核心事实和高优先级任务，而不是让所有请求一起超时。

## Q31. Kubernetes 自动扩缩容为什么不能只看 CPU？

**题型**：高薪平台题  
**实际难度**：中等偏上  
**学习层级**：进阶加分题

### 事故画面

Agent Worker 都在等待模型和数据库，CPU 只有 30%，用户却已经超时。HPA 继续扩 Pod，新增连接和模型请求反而让下游更慢。

### 正确指标

- 在途任务；
- MQ Lag 与最老消息年龄；
- 单 Pod 处理速率；
- P99、拒绝率和队列年龄；
- 模型配额、数据库连接与下游并发；
- 长任务的租约和安全缩容状态。

### 2～3 分钟面试口述回答

HPA 只看 CPU 对 I/O 密集和外部依赖型系统很危险。Worker 可能在等待模型、Milvus 或数据库，CPU 很低但用户已经超时；继续扩 Pod 会增加连接和外部调用，把下游压得更严重。我会结合在途任务、MQ Lag 和最老消息年龄、每 Pod 处理率、P99、拒绝率和下游配额设计扩缩容指标。

扩容要有最大副本、速度和稳定窗口，并与全局并发和租户准入联动。如果下游不能扩，只能限流、排队或降级。缩容前应停止领取新任务、排空连接、完成或移交租约，避免长任务被反复杀死。自动扩容只是容量执行器，不能替代容量模型、背压和依赖保护。

- 长任务如何优雅缩容？

## Q32. Metrics、Logs、Trace 如何分工，高基数为什么危险？

**题型**：高频平台题  
**实际难度**：中等偏上  
**学习层级**：进阶加分题

### 分工

```text
Metrics：低基数趋势、SLO、容量、告警
Trace：一次请求/Run 的因果链和阶段耗时
Logs：结构化事件、错误上下文和审计
```

`runId`、`requestId`、`operationId` 和文档 ID 不应直接作为大规模指标 Label，而应进入 Trace/Log，通过 exemplar 或 traceId 跳转。

### 2～3 分钟面试口述回答

Metrics、Logs 和 Trace 解决不同问题。Metrics 适合低成本聚合趋势、SLO 和告警，维度必须低基数；Trace 适合查看一次请求或 Agent Run 跨服务的因果链；Logs 保存结构化事件、错误上下文和审计。runId、userId、operationId 等取值几乎无限，放到指标 Label 会导致时间序列爆炸，因此应放在 Trace 和日志中。

指标可以按 service、operation、status、tenantTier 和 dependency 等有限维度统计 P99、错误率和队列年龄，再通过 exemplar 或 traceId 跳到具体链路。全链统一传播 deadline、version 和稳定业务 ID，并对 Prompt、Token 和凭据脱敏。可观测性目标是回答原因、用户影响和正确性，而不是收集越多字段越好。

## Q33. 生产事故中止血、留证、定位、恢复和对账的正确顺序是什么？

**题型**：高薪事故题  
**实际难度**：困难  
**学习层级**：70% 必会题

### 处理顺序

```text
止血与冻结发布
→ 指定 Incident Commander
→ 保存证据和时间线
→ 找第一个偏离基线的原因
→ 每次只做可回滚变更
→ 分阶段恢复
→ 业务对账与补偿
→ 复盘转化为门禁
```

### 2～3 分钟面试口述回答

生产事故第一目标是止损，不是立即找到完美根因。先限流、关闭危险功能、保护数据库和不可逆工具，冻结非必要发布。随后由 Incident Commander 统一决策和沟通，记录时间线，并保存配置、指标、Trace、消息位置和业务样本，避免重启后证据消失。

定位时寻找第一个偏离基线的指标，而不是最后一个报错。每次操作都写清预期、观察窗口和回滚条件，分阶段恢复流量。服务变绿后仍要从事实源对账订单、库存、权限、缓存、索引和外部副作用，补偿未完成状态。复盘不能只写“加强监控”，而要形成测试、限流、容量、Runbook、发布门禁和明确负责人。
